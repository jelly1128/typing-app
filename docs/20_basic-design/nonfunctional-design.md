# 非機能設計

`requirements.md` の全 NFR-ID に対する具体的な実現方式を確定する。`system-architecture.md` 6章の対応方針(一覧)を、ここで実装レベルまで具体化する。

## NFR-01 入力反応性(50ms以内)

**実現方式**: ADR-002 のとおり、判定はフロントエンド完結。ネットワーク往復が発生しないため、Vue のリアクティビティによる画面更新のみで反映する。追加の最適化(仮想DOM差分の抑制等)はP5実装時に計測して必要なら行う。

**検証方法**: P6 テスト実施時、ブラウザ開発者ツールの Performance タブ、または簡易な計測用ログで確認する。

## NFR-02 画面表示速度(体感2秒以内)

**実現方式**: バックエンドへの通信は画面遷移時のみ(S-02でのお題文取得、S-04でのセッション結果保存、S-05/S-06でのデータ取得)に限定し、タイピング中(S-03)は通信しない(NFR-01と同じ設計が寄与する)。個人利用のため同時アクセス数は実質1であり、DB・API側の負荷は無視できる規模。

**例外**: Render 無料枠のコールドスタート発生時(NFR-03)は2秒を超えうる。これは許容する。

## NFR-03 可用性の方針

**実現方式**: Render 無料枠の Web Service + Managed PostgreSQL を使用する。一定時間アクセスが無い場合のスリープ、次回アクセス時のコールドスタート遅延(数十秒程度)を許容する。稼働率(SLA)の数値目標は設定しない。

## NFR-04 通信の保護

**実現方式**: Render のデフォルト機能による HTTPS(証明書自動発行)をそのまま利用する。フロントエンド→バックエンドの通信も同じ公開 URL 配下で HTTPS になる。追加のTLS設定は行わない。

## NFR-05 入力値の保護

**実現方式**:
- バックエンド: Spring Data JPA のメソッドクエリ / `@Query` のバインドパラメータを使用し、SQL文字列を連結で組み立てない
- フロントエンド: Vue テンプレートのデフォルトエスケープ(`{{ }}`)に任せ、`v-html` は使用しない(XSS対策)

## NFR-06 秘匿情報管理

**実現方式**: DB接続URL・ユーザー名・パスワードは Render の環境変数機能で管理し、`application.yml` 等にハードコードしない。ローカル開発は Docker Compose の環境変数、または `.env`(`.gitignore` 対象)で管理する。

## NFR-07 ログ

**実現方式**: Spring Boot 標準の Logback(デフォルト設定)で、アプリケーション起動・未処理例外をログ出力する。APM等の追加監視基盤は導入しない。

例外から HTTP 応答への変換は `@RestControllerAdvice` による一元的なハンドラ1箇所に集約する(Controller ごとの個別 try-catch は行わない)。このハンドラが `api-spec.yaml` の `ErrorResponse.traceId`(リクエストごとに発行する一意な文字列)を採番し、レスポンスとログの双方に同じ値を出す。

500(サーバー内部エラー)を返す際、ログに以下を必ず出力する: 発生時刻 / エンドポイントとHTTPメソッド / `traceId` / `userId`(取得できる場合)/ 例外クラス名 / スタックトレース。個人開発の1人運用のため、これ以上のログ基盤(集約・アラート)は導入しない。

## NFR-08 バックアップ

**現状(2026-08-26時点、REV-008 A2)**: 「Render Managed PostgreSQL の標準バックアップ機能に委ねる」は、無料枠で実際にバックアップが提供されるかを未確認のまま前提化していた。P2.5(Walking Skeleton)着手時に、使用する Render プランの Postgres について次の2点をダッシュボードで確認し、結果に応じて本節を更新する(`docs/00_project/wbs.md` P2.5 節にタスクとして記載)。

- 自動バックアップ(スナップショット/PITR)の有無
- インスタンス自体の有効期限の有無

確認後は次のいずれかを採用する: (a) 提供される→保持期間を明記して現行方針を維持、(b) 提供されない→`operation.md`(REL-002)に手動 `pg_dump` の手順を残す、(c) 対応しない→「本番データは消えうる。消えたらシードデータから作り直す」ことを `charter.md` 6章の受入リスクに追記する。

## NFR-09 DB障害時の挙動

**実現方式**: `POST /api/sessions`(FR-07)は `@Transactional` でトランザクション境界を明示し、保存失敗時は 500 エラーを返す(`api-spec.yaml` 参照)。フロントエンドは 500 応答を受けて S-04 にエラー表示を出す(`screen-design.md` S-04 に記載済み)。

**方針の一般化(2026-08-26 改訂、REV-007 A2 / REV-008 B6 対応)**: 5xx を返すのは DB接続断・未処理例外などサーバー側の障害に限定する。以下は 5xx と区別し、`api-spec.yaml` にエンドポイントごとの400/404として定義する。

- **400(入力値の不正)**: 必須項目欠落・値域外・enum外・リクエスト内の整合性違反(例: `missRecords` が `kanaCounts` に無いかなを参照する)
- **404(リソース不在)**: 指定した `userId` / `topicSetId` が存在しない

DB接続断時は個別のフォールバック処理を作らず一様に 500 を返し、フロントエンドは各画面で「読み込みに失敗しました」等の汎用エラー表示に切り替える。自動リトライ・フェイルオーバーは行わない。

**userId が存在しない場合のフロントエンド側の挙動**: `screen-design.md` 2章参照(404 受信時に localStorage をクリアし S-01 へ戻す)。
