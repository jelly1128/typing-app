# ローマ字入力受理オートマトン仕様

対応 FR: FR-02(ローマ字入力判定・複数表記許容)、FR-03(リアルタイム表示)、FR-04(ミス記録)

言語非依存の疑似コードで記述する(`CLAUDE.md` の制約: `typing-core` は Java、実働の判定エンジンは TypeScript フロントエンドだが、本仕様はどちらの実装にも移植できる形で書く)。

---

## 1. 目的とスコープ

お題の読み(かな列)を「拍(はく)」の並びに分解し、利用者のキー入力を1キーずつ判定して、以下を実現する。

- 同一の拍に対する複数のローマ字表記を正解として許容する(FR-02)
- キー入力のたびに「確定済み文字」「次に打つべき文字」「ミス位置」を更新できる情報を出す(FR-03)
- ミスが発生した拍・期待していたキー・実際に入力されたキー・直前の拍・文字種タグを記録できる情報を出す(FR-04)

対象外: かな漢字変換・IME・カーソル移動やBackspaceなどの編集操作(FR-02の前提により、IMEを介さない直接キー判定のみを扱う)。

---

## 2. 用語

`glossary.md` 1〜2章を前提とする。特に以下を再確認する。

- **拍**: ミス記録・分析の単位。清音は1文字、拗音は2文字(例: しゃ)で1拍
- **キー入力**: 判定の最小単位。ローマ字アルファベット1文字
- **文字種**: 清音 / 拗音 / 撥音「ん」/ 促音「っ」/ 長音「ー」の5分類(ミス記録のタグ)

---

## 3. データモデル

```
構造体 拍(Mora):
    かな表記        // 例 "し"、"しゃ"、"っ"、"ん"、"ー"
    文字種          // 清音 | 拗音 | 撥音ん | 促音っ | 長音

構造体 拍列(MoraSequence):
    拍の配列          // お題データの mora_list をそのまま使う(下記「前提」参照)
```

**前提:** お題文をかな列から拍列へ分解する処理(形態素解析ではなく、かな1文字ずつを清音/拗音/ん/っ/ーに機械的に分類する処理)は本仕様の対象外とする。`table-definition.md` TBL-03 の `mora_list` 列に、お題データ作成(シードデータ投入)時点で拍列として保持しておく(2026-08-29、ゲート③ test-reviewer A4対応、CL-012)。理由: お題は開発者が投入する固定データであり(FR-13備考)、実行時の自動分割ロジックを持つ必要がない。判定エンジンは `api-spec.yaml` の `Sentence.moraList` をそのまま `MoraSequence` として受け取る。

## 5. 特殊カテゴリの受理ロジック

### 5.1 撥音「ん」

```
関数 んの受理パターン(次の拍):
    もし 次の拍が存在しない(文末):
        戻り値 = {"n", "nn"}

    次の拍の先頭文字候補 = 次の拍の受理パターン一覧(4章の表、または次の拍自身が特殊カテゴリならその関数)の
                          各パターンについて先頭1文字を取り出した集合

    もし 次の拍の先頭文字候補 に "a","i","u","e","o","y","n" のいずれかが含まれる:
        // 母音・"y"で始まる場合: 例 "きんえん"のん→"ki"+"nn"+"en"("kinen"だと"きねん"と区別できない)
        // "n"で始まる場合(な行): 例 "こんにちは"のん→"ko"+"nn"+"nichiwa"("konichiwa"だと"n"が1つ「に」に食われて別物になる)
        戻り値 = {"nn"}
    それ以外:
        戻り値 = {"n", "nn"}
```

**根拠:** ローマ字表記において "n" 単体は、次にくる文字が母音・"y"・**"n"自身**のいずれかで始まる場合に、その文字と結合して別の拍に読めてしまう。次の拍が「な行」(な/に/ぬ/ね/の、いずれも"n"で始まる)の場合も、「ん」の"n"と次拍の先頭"n"が衝突する点で母音・や行と同じ性質の曖昧さを持つため、"nn"を必須にする。

**2026-08-29改訂(P3中間レビューREV-009 B6対応):** 当初は「母音行(あ/や行)/子音行(それ以外)」という2分類で判定しており、な行を「子音行」に含めていた。しかしな行自体が"n"で始まるため、上記と同じ衝突が起きる欠陥があった。3章にあった`子音種別`という固定属性を廃止し、代わりに次の拍の受理パターンを実際に見て先頭文字を判定する方式に改めた(な行以外にも、将来受理表が変わって"n"始まりの表記が増えた場合にも自動的に対応できる)。

### 5.2 促音「っ」

促音の入力方法は2種類ある。

1. **子音重ね方式(主)**: 次の拍の子音を1文字重ねて入力する(例: がっこう→ga+kko+uの"kk")。この方式では、促音の1キーと次拍の先頭子音が同一でなければならない
2. **独立表記方式(副、"たまに使う"表記)**: 次の拍と無関係に、"xtu" / "xtsu" / "ltu" / "ltsu" のいずれかで促音そのものを確定する(次の拍の表記には一切影響しない)

```
関数 っの受理パターン(次の拍):
    次の拍候補群 = 次の拍の受理パターン一覧(4章の表を参照)
    子音重ね候補 = 次の拍候補群の各パターンについて先頭1文字を取り出し、重複を除いた集合
    独立表記候補 = {"xtu", "xtsu", "ltu", "ltsu"}
    戻り値 = 子音重ね候補 ∪ 独立表記候補
    // 例: 次拍が「し」(si/shi/ci) → 戻り値 = {"s", "c", "xtu", "xtsu", "ltu", "ltsu"}

関数 次の拍の受理パターンを絞り込む(次の拍候補群, っで確定したパターン):
    もし っで確定したパターンの文字数 == 1:   // 子音重ね方式で確定した場合のみ絞り込む
        戻り値 = 次の拍候補群のうち、先頭文字が っで確定したパターン と一致するものだけ
        // 例: っで "s" を確定した場合、次拍「し」は si/shi のみ許容(ci は不許可)
    それ以外(独立表記方式で確定した場合):
        戻り値 = 次の拍候補群（絞り込まない。次拍は通常どおり全表記を許容）
```

**根拠:** 子音重ね方式は促音のキーと次拍の綴りが物理的に同一文字である必要があるため、っを先に確定させてから次拍候補を絞り込む。一方、独立表記方式(x/l + tu/tsu)は次拍の入力とは無関係に完結するため、次拍の候補を絞り込まない。両者は`っの受理パターン`が返す集合の中で長さで区別できる(子音重ね候補は必ず1文字、独立表記候補は3〜4文字)ため、6章の判定オートマトンは分岐を1箇所追加するだけで両方式に対応できる。

**前提とする制約(お題データ側):** 促音は必ず子音行の拍の直前にのみ出現する(母音行・や行・撥音ん・長音ーの直前には出現しない)。この前提が崩れるお題データは投入しない。

### 5.3 長音「ー」

**設計判断:** 実在の日本語ローマ字入力系タイピングソフト(e-typing 等)に倣い、長音記号「ー」は**直前の拍の母音とは独立した、"-"(ハイフン)キー1つで確定する固定の拍**として扱う([ADR-004](../../00_project/decisions/004-long-vowel-hyphen-key.md)で確定。P1の`requirements.md`/`glossary.md`にあった「直前の母音を繰り返す」方式を上書きしたため、両文書も合わせて修正済み)。

```
関数 ーの受理パターン():
    戻り値 = {"-"}
```

理由: 「直前の母音を繰り返す」方式(例: コーヒー→"koohii")は、直前の拍が複数表記を持つ場合(例: し→si/shi/ci)にどの母音表記を延長するかの組み合わせが増え、実装・テストベクタの複雑さに見合わない。既存の日本語タイピングソフトの多くも "-" キー1つに統一しており、学習者にとっても直感的(用語集にある「文字種」タグとしての「長音」の扱いにも影響しない)。

## 6. 判定オートマトン(疑似コード)

**2026-08-29改訂(P3中間レビューREV-009 A2/A3対応):** 当初案は「入力済み文字列が候補と完全一致した瞬間に確定する」という規則だったが、`{"n", "nn"}`のように一方が他方の真の接頭辞になる候補が混在するケース(撥音ん)で、短い方(`"n"`)が必ず先に確定してしまい`"nn"`に到達できない欠陥があった。以下は、候補が複数残っている間は確定を保留し、次のキーで延長されるか他の拍へ「押し戻す」かを判断する形に改めたものである。あわせて、促音の絞り込み結果(5.2)を次の拍の判定へ実際に引き渡す配線を明記した。

拍列全体を処理する外側のループと、1拍を確定させるまでキー入力を読み進める内側のループの2層で構成される。**「次のキー入力を待つ」は概念上の表現であり、実装(`class-design.md` 2.2 `sequenceJudge.ts`)ではキー入力イベントが発生するたびに1回だけ呼ばれる関数として書く。その際、本節の変数(候補集合・入力済み文字列・保留中の確定候補・持ち越しキー・直前に確定した拍・累計拍インデックス等)は全て呼び出しをまたいで保持するインスタンスの状態になる**(2026-08-29、ゲート③検証レビューREV-013 A4対応)。

### 6.0 拍列全体のループ

```
関数 拍列を判定する(拍列):
    次拍への絞り込み候補 = なし   // 直前の拍が促音っで、次拍の候補を絞り込んだ場合のみ値が入る
    持ち越しキー = なし          // 前の拍の判定中に「押し戻された」キー(あれば次の拍の1手目として使う)

    forEach 番号 i (0 から 拍列.length-1 まで):
        現在の拍 = 拍列[i]
        次の拍   = 拍列[i+1]（存在する場合のみ）
        結果 = 拍を判定する(現在の拍, 次の拍, 事前絞り込み候補 = 次拍への絞り込み候補, 先頭キー = 持ち越しキー)
        次拍への絞り込み候補 = 結果.次拍への絞り込み候補   // 促音っ以外は常に なし
        持ち越しキー = 結果.持ち越しキー                    // 押し戻しが発生しなければ なし
```

### 6.1 1拍を確定させるループ

```
関数 拍を判定する(拍, 次の拍, 事前絞り込み候補, 先頭キー):
    受理パターン集合 =
        もし 事前絞り込み候補 が なし でない: 事前絞り込み候補
        それ以外 もし 拍の文字種 == 撥音ん  ならば んの受理パターン(次の拍)
        それ以外 もし 拍の文字種 == 促音っ  ならば っの受理パターン(次の拍)
        それ以外 もし 拍の文字種 == 長音  ならば ーの受理パターン()
        それ以外                          ならば 4章の表から引いた集合

    入力済み文字列 = ""
    候補集合 = 受理パターン集合
    保留中の確定候補 = なし   // 完全一致したが、まだ長い候補が残っているため確定を待っている状態

    ループ:
        もし 先頭キー が なし でない かつ 今回が最初の反復:
            キー = 先頭キー   // 前の拍から押し戻されたキーを1手目として使う
        それ以外:
            キー = 次のキー入力を待つ

        試行後文字列 = 入力済み文字列 + キー
        新候補集合 = { p ∈ 候補集合 | p は 試行後文字列 で始まる }

        もし 新候補集合 が空:
            もし 保留中の確定候補 が存在する:
                // 保留していた短い方を確定し、今回のキーは次の拍の1手目として押し戻す
                次拍への絞り込み候補 = この拍を確定する(拍, 採用パターン = 保留中の確定候補)
                戻り値 = { 次拍への絞り込み候補 = 次拍への絞り込み候補, 持ち越しキー = キー }
                ループを抜ける(この拍の判定を終了する)
            それ以外:
                // ミス: 正しいキーが入力されるまで先に進めない(FR-02受け入れ条件)
                ミスを記録する(
                    対象拍 = 拍,
                    期待キー候補 = { p[入力済み文字列の長さ] | p ∈ 候補集合 },
                    実際キー = キー,
                    直前拍 = 直前に確定した拍,
                    文字種タグ = 拍の文字種
                )
                // 入力済み文字列は変えない(誤ったキーは捨てて再入力を待つ)
                継続

        それ以外:
            入力済み文字列 = 試行後文字列
            候補集合 = 新候補集合

            もし 候補集合の中に 入力済み文字列 と完全一致するパターンが存在する:
                もし 候補集合の要素数 == 1 または 次の拍 が存在しない:
                    // これ以上延長される候補がない、または延長を待つ相手(次の拍)がない → 即確定
                    次拍への絞り込み候補 = この拍を確定する(拍, 採用パターン = 入力済み文字列)
                    戻り値 = { 次拍への絞り込み候補 = 次拍への絞り込み候補, 持ち越しキー = なし }
                    ループを抜ける(この拍の判定を終了する)
                それ以外:
                    // 完全一致はしたが、まだ長い候補(例: "n"に対する"nn")が残っている → 確定を保留
                    保留中の確定候補 = 入力済み文字列
                    継続
            それ以外:
                継続   // まだ複数候補が残っている、または1候補の途中(次のキーを待つ)

関数 この拍を確定する(拍, 採用パターン):
    直前に確定した拍 = 拍   // セッション全体で持ち回る状態。次の拍のミス記録で使う
    累計拍インデックス += 1  // セッション全体で持ち回る状態。お題文をまたいでもリセットしない(7.1)
    次拍への絞り込み候補 = なし
    もし 拍の文字種 == 促音っ:
        次拍への絞り込み候補 = 次の拍の受理パターンを絞り込む(次の拍の受理パターン一覧 = 4章の表から引いた集合, っで確定したパターン = 採用パターン)
    戻り値 = 次拍への絞り込み候補
```

**「文末で次の拍が存在しない」場合の扱い:** 5.1のとおり、文末の撥音んは`{n, nn}`のどちらも許容される。上記ループでは「候補集合の要素数==1 または 次の拍が存在しない」の後半の条件により、文末では最初に完全一致した時点(通常は"n"を打った瞬間)で即確定し、"nn"への延長を待たない。文末より後にキーが来ることは無い(次のお題またはセッション終了に進む)ため、これでよい。

**FR-03(リアルタイム表示)との対応(2026-08-29、ゲート③ doc-reviewer A5/test-reviewer A1対応で確定):** 「確定済み文字」は確定済み拍までの表記(採用パターンで表示)。「次に打つべき文字」は**動的選択方式**とする: `候補集合`の中から**最も文字数が短いパターンを選び(同じ文字数のものが複数あれば辞書順で先頭)**、そのうち`入力済み文字列`の長さ分を除いた残りの部分だけを表示する(例: 「し」の候補`{si, shi}`で`s`まで入力済みなら、より短い`si`の残り`i`を表示する。`shi`の残り`hi`は表示しない。**候補集合が絞り込まれるたびに選び直す**ため、候補が減るとヒントも変わりうる。2026-08-29、ゲート③検証レビューREV-013 A2対応: 当初「辞書順で先頭」としていたが直後の例と矛盾していたため「最短優先」に確定)。

**`KeystrokeResult`への反映(2026-08-29、REV-013 A1対応):** `この拍を確定する`が呼ばれたキー入力では`KeystrokeResult.confirmedMora`にその内容(かな・文字種・採用パターン・累計拍インデックス)を入れる(呼ばれなければ`null`)。`ミスを記録する`が呼ばれたキー入力では`KeystrokeResult.miss`にその引数一式を入れる(呼ばれなければ`null`)。両方とも`null`のキー入力(継続中・ヒット更新のみ)もありうる。フィールドの詳細は`class-design.md` 2.2参照。「直近のミス位置」はミス記録の`対象拍`(次に正しいキーが入力された時点でクリアする)。この規則の実装先は`class-design.md` 2.2の`sequenceJudge.ts`(6.1の疑似コード全体の実装先。`KeystrokeResult`にヒント文字列を含める。`moraJudge.ts`は候補の絞り込み・完全一致判定の部分手順のみを提供する無状態ヘルパー)。

**既知の制限: 1キーで2拍が同時に確定するケース(2026-09-07、コードレビューで発見)。** `押し戻し`(A2対応)によって直前の拍が確定し、かつ**押し戻されたキーが次の拍をも単独で即時確定させる**場合、1回のキー入力で2つの`この拍を確定する`が呼ばれる。しかし`KeystrokeResult.confirmedMora`は1件しか保持できないため、この場合は押し戻された側(古い方)の拍の確定イベントが`KeystrokeResult`に反映されない(`confirmedText`・内部の拍列位置自体は正しく進む。失われるのは`sessionStore`向けの「確定イベント」の通知のみ)。

この条件を満たすには、次の拍の受理パターン集合が要素数1で、かつ押し戻されたキー(1文字)がそのパターンと完全一致している必要がある。実在するかな受理表(4章)ではこれは長音「ー」(候補`{"-"}`固定)が撥音「ん」の直後に続く場合にのみ起こりうるが、「ん」は母音を持たないため「ー」で伸ばす対象にならず、実在の日本語のお題データでこの並びが登場することは無いと考えられる。そのため**現時点では対応せず、既知の制限として記録するにとどめる**(Kazuki合意、2026-09-07)。将来`KeystrokeResult.confirmedMora`を配列に変更する等の対応が必要になった場合は、`class-design.md` 2.2・`test-plan.md` 3.1のRA-xxxスキーマも合わせて改訂すること。

### 6.2 具体例で理解する

疑似コードだけでは動きが掴みにくいため、実際に1キーずつ入力していく様子を追う。**やっていることは「まだ正解になり得る綴りの候補を、キーが打たれるたびに絞り込んでいく」だけ**である。1文字目を打った時点ではどの表記で打つつもりかは分からないため、候補を複数持っておく必要がある。

**例1: 「し」を打つ(候補は `{si, shi, ci}` から始まる)**

| 状況 | 打ったキー | 絞り込み後の候補 | 判定 |
|---|---|---|---|
| 開始 | - | `{si, shi, ci}` | まだ何も打っていない |
| 1手目 | `s` | `{si, shi}`(`ci`は`s`で始まらないため脱落) | 複数残っている。継続 |
| 2手目 | `i` | `{si}`(`shi`は2文字目が`h`のため脱落) | 入力済み文字列`si`が候補と完全一致 → **確定** |

もし1手目で`x`のようにどの候補にも一致しないキーを打つと、絞り込み後の候補が空になる。この時点でミスとして記録し、入力済み文字列は変えずに正しいキーを待つ(FR-02「正しいキーが入力されるまで先には進めない」)。

**例2: 「っこ」を打つ(促音の2方式が分岐する)**

次の拍「こ」の綴りは`ko`のみなので、「っ」の候補は子音重ね方式`{k}`と独立表記方式`{xtu, xtsu, ltu, ltsu}`を合わせた`{k, xtu, xtsu, ltu, ltsu}`。

子音重ねで打つ場合:

| 状況 | キー | 候補 | 判定 |
|---|---|---|---|
| 開始 | - | `{k, xtu, xtsu, ltu, ltsu}` | |
| 1手目 | `k` | `{k}` | 完全一致 → **確定**(1文字なので子音重ね方式) |

確定パターンが1文字だったので、次の「こ」の候補は「`k`で始まる綴りだけ」に絞り込まれる(今回は`ko`しかないので実質変化なし)。この絞り込み結果は`この拍を確定する`の戻り値として6.0の外側ループに渡り、次の拍の`拍を判定する`呼び出しに`事前絞り込み候補`として引き継がれる。

独立表記で打つ場合:

| 状況 | キー | 候補 | 判定 |
|---|---|---|---|
| 開始 | - | `{k, xtu, xtsu, ltu, ltsu}` | |
| 1手目 | `x` | `{xtu, xtsu}` | 複数残っている。継続 |
| 2手目 | `t` | `{xtu, xtsu}` | 変わらず継続 |
| 3手目 | `u` | `{xtu}` | 完全一致 → **確定**(3文字なので独立表記方式) |

確定パターンが3文字以上だったので、次拍の候補は絞り込まれない。次が「し」のような複数表記のかなであれば`si/shi/ci`が全て残る。

**例3: 「こんばんは」の「ん」を打つ(押し戻しが発生するケース、A2対応)**

「ん」の次拍は「ば」(子音行)なので候補は`{n, nn}`。**この2つは一方が他方の接頭辞になっている点が他の例と違う。**

「n」で単独確定させる打ち方(`...ko` → `n` → `ba...`):

| 状況 | キー | 入力済み文字列 | 候補 | 判定 |
|---|---|---|---|---|
| 開始 | - | `""` | `{n, nn}` | |
| 1手目 | `n` | `"n"` | `{n, nn}`(両方とも`"n"`で始まる) | `"n"`は候補と完全一致するが、候補が2つ残っており次の拍(ば)も存在する → **保留**(確定しない) |
| 2手目 | `b` | (保留のまま。`"nb"`はどの候補にも一致しない) | 新候補集合が空 → 保留中の候補`"n"`を確定し、`b`は次の拍(ば)へ**押し戻す** | 「ん」= `"n"`で確定。次の拍の判定が`b`を1手目として開始する |

「nn」で明示的に伸ばす打ち方(`...ko` → `n` → `n` → `ba...`):

| 状況 | キー | 入力済み文字列 | 候補 | 判定 |
|---|---|---|---|---|
| 開始 | - | `""` | `{n, nn}` | |
| 1手目 | `n` | `"n"` | `{n, nn}` | 完全一致だが候補2つ・次拍あり → **保留** |
| 2手目 | `n` | `"nn"` | `{nn}`(`"n"`は`"nn"`を含む2文字目に伸ばせないため脱落) | 候補が1つに絞られた → **確定**(`"nn"`) |

もし6章の当初案(完全一致した瞬間に確定)のままだったら、1手目の`n`で即座に「ん」が`"n"`確定してしまい、2手目の`n`は「ば」の1手目としてしか評価されなくなる。「ば」の候補は`{ba}`しかないため、`n`はどの候補にも一致せず**ミスとして誤記録**され、実際にはよく使われる`"nn"`という打ち方が常に失敗扱いになっていた。保留・押し戻しの仕組みは、この欠陥を解消するために導入した。

### 7.1 セッション記録の生成規則(2026-08-29、ゲート③ doc-reviewer A4/test-reviewer A3対応で確定)

`api-spec.yaml` の `SessionSubmission` が要求する項目のうち、次の5つは本仕様(判定エンジン)の外側、`class-design.md` 2.4 `sessionStore` の責務として生成する。生成規則をここに確定する(採用場所を分けたのは、判定エンジン自体は「1拍の正誤判定」に閉じ、セッション全体にまたがる集計は状態を持つ`sessionStore`側の責務とするため)。

| 項目 | 生成規則 |
|---|---|
| `kanaOccurrenceNo`(ミス記録) | `sessionStore` が「かなの種類ごとのカウンタ」のマップを持つ。**`KeystrokeResult.moraIndex` が直前の値から変化した時点**(=新しい拍の判定が始まった時点。`class-design.md` 2.2参照)でその拍のかなのカウンタを+1し、その値をこの拍の判定が終わるまで保持する。この拍で発生した全てのミス記録は、この値を`kanaOccurrenceNo`として使う。**かなの種類ごとのカウンタは、お題文をまたいでもリセットしない**(お題文単位の分析を要求するFRが無く、カウンタ1つで実装がシンプルになるため)。2026-08-29改訂(ゲート③検証レビューREV-013 A3対応): 当初トリガを`currentKana`の変化としていたが、「おおきい」のように同じかなが連続する拍で新しい拍の開始を検知できない欠陥があり、拍そのものの通し番号である`moraIndex`の変化をトリガに変更した |
| `prevKana`(ミス記録) | `sequenceJudge`が既に内部状態として持つ「直前に確定した拍」(6.1 `この拍を確定する`)をそのまま使う。**セッション最初の拍のみNULL、以降はお題文をまたいでも前の文の最後の拍を引き継ぐ**(kanaOccurrenceNoと同じ理由で、お題文の切れ目をリセット境界にしない) |
| `correctKeyCount` | 拍が確定するたび、採用パターンの文字数を加算する(例:「し」を`shi`で確定したら+3)。ミスとして記録されたキー入力はここに含めない |
| `keystrokeIntervalsMs` | 正誤を問わず、隣接する2キー入力イベントの発生時刻の差[ms]を記録した配列。セッション内の総キー入力回数(ミス含む)をNとすると要素数はN-1(最初のキー入力には直前が無いため) |
| `kanaCounts[].totalCount` | 拍が**確定した**回数(出題された回数ではない)。制限時間モードで打鍵途中のまま終了条件に達した拍は、確定していないためカウントしない(`session-metrics.md`・`sequence.md`のFR-05終了条件判定と合わせる) |

## 9. `shared/testdata` への申し送り

本仕様の正しさは、P5実装時に以下の形でテストベクタ化して検証する(CLAUDE.mdの制約: ロジックコアは共有テストベクタで他言語へ移植可能にする)。

- 4章の表の全行 × 各受理パターン → 正しく確定できること
- 5.1 撥音んの分岐(次拍が母音行/や行/子音行/文末それぞれ) → "n"単体の受理可否が仕様どおりであること
- **6章の押し戻し(A2対応)**: 「ん」を`n`単体で打って次拍へキーが押し戻されるケース、`nn`と伸ばして確定するケースの両方が正しく判定されること(6.2 例3)。文末の「ん」は`n`単体で即確定すること
- **5.1のな行分岐(B6対応)**: 次の拍がな行(な/に/ぬ/ね/の)の場合、単独の`n`では確定できず`nn`が必須になること(例: 「こんにちは」の「ん」は`nn`でのみ受理される)
- **6章の絞り込み配線(A3対応)**: 促音っを子音重ね方式で確定した際、その結果が実際に次拍の`拍を判定する`呼び出しへ伝播し、次拍の表記ゆれが正しく絞られること(例: っし → s/c の一貫性)。独立表記方式(xtu/xtsu/ltu/ltsu)で確定した場合は次拍の表記が絞り込まれず全パターン許容されること
- 誤入力時にミスとして記録され、正しいキーが入力されるまで進まないこと(6章)
- **7.1 セッション記録生成規則**: `kanaOccurrenceNo`がお題文をまたいでもリセットされず通し番号になること、`prevKana`がセッション最初の拍のみNULLで以降はお題文をまたいでも維持されること、**同じかなが連続する拍(例: 「おおきい」の「お」×2)でも`moraIndex`の変化により正しく別の出現として区別されること**(REV-013 A3対応)
- **6.1末尾 画面ヒント**: 候補が絞り込まれるたびにヒント表示が動的に変わること(例: 「し」で`s`入力後は`i`だけが残候補になること)

具体的なテストベクタ一覧はP4(テスト設計)で作成する。
