# 改善アドバイス生成仕様

対応 FR: FR-11(改善アドバイスを表示する)

言語非依存の疑似コードで記述する。入力は `api-spec.yaml` の `MissAnalysis`(FR-10の4観点)、出力は同スキーマの `advice` フィールド(文字列の配列、0〜3件)。

> **2026-08-29 変更(CL-005):** 当初は優先順位の高い1件だけを返す設計だったが、Kazukiの要望により「該当するカテゴリすべてを独立に返す」複数アドバイス方式に変更した。確定済みだった`api-spec.yaml`(BD-003)・`screen-design.md`(BD-002)の該当箇所も合わせて修正済み(`change-log.md` CL-005)。

---

## 1. 入力データ

`GET /api/users/{userId}/miss-analysis` が算出した4観点(`api-spec.yaml` `MissAnalysis`)をそのまま使う。全期間・全難易度の累積データである点に注意(特定セッション単体の分析ではない)。

```
構造体 分析結果(MissAnalysis):
    byKana          // [{kana, missCount, missRate}]  多い順
    byErrorPattern  // [{expectedKey, actualKey, count}]  多い順
    byPrevKana      // [{prevKana, missRate}]  多い順
    byCharType      // [{charType, occurrenceCount, accuracyRate}]  出現回数0の文字種は含まれない(0〜5件、api-spec.yaml CL-007)
```

---

## 2. 生成方針: カテゴリごとに独立判定する複数アドバイス

3つのカテゴリ(誤りパターン/かな別/文字種別)を**それぞれ独立に判定**し、閾値を満たしたものだけを配列に集める(最大3件)。1つのカテゴリが該当してもほかのカテゴリの判定は打ち切らない(優先順位による排他選択ではない)。表示順は「具体的で対処しやすい順」(誤りパターン→かな別→文字種別)に揃える。

**採用しなかった観点: `byPrevKana`(直前のかな別ミス率)はアドバイス生成には使わない。** 「直前が『か』の時にミスしやすい」という情報は事実として正しくても、「では何を練習すればよいか」という具体的な行動に機械的に変換しにくく、テンプレート化するとかえって分かりにくい文になるため対象外とした(却下理由。画面上には分析結果自体は表示されるため、情報が失われるわけではない)。

### 判定ロジック(3カテゴリを独立に評価し、該当したものを配列に集める)

```
関数 アドバイスを生成する(分析結果):
    もし 分析結果の全観点が空(セッション0件):
        戻り値 = []   // api-spec.yaml「セッション自体が0件の場合...adviceは空配列」

    結果 = []

    // カテゴリ1: 誤りパターン(最も具体的で対処しやすい)
    もし byErrorPattern が空でない かつ byErrorPattern[0].count >= 3:
        結果に追加(テンプレート適用("pattern", byErrorPattern[0]))

    // カテゴリ2: かな別ミス
    もし byKana が空でない:
        対象 = byKana[0]
        総出現回数(推定) = 対象.missCount ÷ (対象.missRate ÷ 100)
        もし 対象.missCount >= 2 かつ 対象.missRate >= 30 かつ 総出現回数(推定) >= 5:
            結果に追加(テンプレート適用("kana", 対象))

    // カテゴリ3: 文字種別正解率(最も粗いが、傾向としては分かりやすい)
    もし byCharType が空でない:
        文字種別の中で accuracyRate が最も低いもの = byCharTypeをaccuracyRate昇順で1件選ぶ(同率なら先に定義順=清音/拗音/撥音ん/促音っ/長音の順)
        もし 文字種別の中で accuracyRate が最も低いもの.accuracyRate < 80 かつ 文字種別の中で accuracyRate が最も低いもの.occurrenceCount >= 5:
            結果に追加(テンプレート適用("charType", 文字種別の中で accuracyRate が最も低いもの))

    // どのカテゴリも該当しなかった場合のみ、称賛メッセージ1件を返す
    もし 結果が空:
        結果 = [テンプレート適用("good", なし)]

    戻り値 = 結果
```

3カテゴリすべてが該当すれば最大3件、1件も該当しなければ`good`の1件のみを返す。`good`と具体的な指摘が混在することはない。

## 3. メッセージテンプレート

| キー | テンプレート文 | 埋め込み値の丸め |
|---|---|---|
| `pattern` | 「"{expectedKey}"を"{actualKey}"と入力してしまうミスが目立ちます(直近の集計で{count}回)。次にこの組み合わせが出たら意識してみましょう。」 | countは整数のまま |
| `kana` | 「「{kana}」のミスが多いです(ミス率{missRate}%)。この文字を含む単語を重点的に練習してみましょう。」 | missRateは整数に丸め |
| `charType` | 「{charType}の正解率が{accuracyRate}%とやや低めです。{charType}を含むお題を選んで練習すると効果的です。」 | accuracyRateは整数に丸め |
| `good` | 「目立った苦手は見つかりませんでした。この調子で練習を続けましょう。」 | 埋め込みなし |

`good` テンプレートは「セッションはあるがミス記録が0件」の場合(api-spec.yaml記載の byCharType 全件 accuracyRate=100 のケース)にも、優先度1〜3のいずれの閾値も満たさないため自然に選ばれる。専用の分岐は不要。

## 4. 設計判断メモ

| # | 判断内容 | 却下した代替案 | 理由 |
|---|---|---|---|
| 1 | `byPrevKana` はアドバイス生成に使わない | 4観点すべてを何らかの形でアドバイスに反映する | 「直前の文字」という条件付きの傾向は具体的な練習行動に変換しにくく、テンプレート化すると分かりにくくなるため。分析結果自体は画面表示されるため情報は失われない |
| 2 | 3カテゴリを独立判定し、該当したものすべてを配列で返す(2026-08-29、Kazuki要望で単一選択方式から変更) | 優先順位の最も高い1件だけを返す(当初案) | 複数の弱点があるなら全部教えてほしいというフィードバックのため。3カテゴリという上限があるので配列でも表示が破綻しない |
| 3 | 閾値(パターン3回、かな率30%+最低出現5回、文字種正解率80%+最低出現5回)は暫定値 | データに基づく統計的な閾値決定 | MVPの個人開発であり、実運用データがまだ存在しない。P6テスト実施やP8振り返りで体感と合わなければ調整する前提の暫定値とする |
| 4 | 文字種別カテゴリにも、かな別カテゴリと同じ最低出現回数(5回)の閾値を課す(2026-08-29、P3中間レビューREV-009 A4対応) | 出現回数を問わずaccuracyRate最小のものを採用 | `occurrenceCount`追加(CL-007)により、出現1回でミス1回=正解率0%のような統計的に無意味な値がそのままアドバイスに使われるのを防ぐため |

## 5. `shared/testdata` への申し送り

- カテゴリ1〜3それぞれが単独で該当する典型的な入力パターン(閾値ちょうど・閾値未満の境界値含む)
- byCharTypeに出現回数0の文字種が含まれない前提でカテゴリ3が正しく動作すること、および出現回数1〜4件(閾値未満)のケースでカテゴリ3が該当しないこと
- 全観点が空(セッション0件)→ advice=[]
- セッションはあるが全観点が空/正解率100(ミス記録0件)→ `good` の1件のみ
- 2カテゴリ以上が同時に該当する場合、両方が配列に含まれ、表示順が「誤りパターン→かな別→文字種別」の順になること

具体的なテストベクタ一覧・閾値の妥当性検証はP4(テスト設計)・P6(テスト実施)で行う。
