# 運用手順

個人開発・学習目的のプロジェクトであり、継続的な保守運用は前提としない(`deployment.md` 1章と同じ判断)。ここでは「何か起きた時に、どこを見て、何ができるか」を最小限まとめる。

## 1. サービス構成

`deployment.md`参照。フロントエンド(Static Site)・バックエンド(Web Service、Docker)・DB(Render Postgres)の3サービス構成。

## 2. 障害対応手順

### 2.1 エラー画面が出た場合(traceIdの使い方)

各画面のエラー表示には、バックエンドで発生したエラーの`traceId`が「(エラーコード: xxxx)」の形で併記される(取得できる場合のみ)。問い合わせを受けたら、まずこの`traceId`を聞く。

1. Renderダッシュボードでバックエンド(Web Service)のログを開く
2. `traceId=<エラーコード>`で検索する(`GlobalExceptionHandler`が`traceId`をログに出力する、NFR-07)
3. 同じ行にログレベル(ERROR/WARN)とエンドポイント・例外内容が出るので、原因を確認する

### 2.2 症状別チェックリスト

| 症状 | 主な原因 | 確認・対応 |
|---|---|---|
| 初回アクセスが遅い(数十秒〜) | バックエンドのコールドスタート(15分無通信でスピンダウン、NFR-03で受入済み) | 待つ。90秒でタイムアウトするが(`class-design.md` 2.3)、通常は復帰する |
| 画面全体が真っ白 | フロントエンドのビルド・デプロイ失敗 | RenderダッシュボードでStatic Siteのビルドログを確認 |
| APIが404 (USER_NOT_FOUND) | DBが再作成され、localStorageのuserIdが古いまま(3章参照) | 仕様どおりの挙動。名前を再入力してもらう |
| APIが500 | サーバー内部エラー | 2.1の手順で`traceId`からログを追う |
| DBに繋がらない | Render Postgresの失効(3章)、接続情報の設定ミス | Renderダッシュボードでインスタンス状態を確認。`deployment.md` 4章の環境変数を再確認 |

## 3. ログ・接続まわりの前提(P3ゲート③ opsレビューC4対応)

- **Renderのログは無期限には残らない。** 障害報告を受けたら日を空けずその場で確認する。ログの保持期間を延ばす監視基盤は導入しない(個人開発の規模には過剰なため、現行方針のままでよいと判断済み)
- **DB接続タイムアウト(HikariCPの既定値、30秒)は明示的に短くしない。** Render Postgres側の状態によっては2.2の「コールドスタート」と重なり体感待ち時間が伸びることがあるが、想定内の挙動とする

## 4. バックアップ・データ復旧(NFR-08受入リスクの運用対応)

**Render無料プランはバックアップ非対応で、DBは作成から30日+猶予14日で自動失効する。** `nonfunctional-design.md` NFR-08で受入リスクとして確定済み。

DBが失効・再作成された場合の実際の挙動:

- **お題マスタ(topic_sets/sentences)は自動復元される。** Flywayの`R__`(繰り返し可能マイグレーション)としてリポジトリにコミットされているため、Flyway実行時に自動投入される(`db-access.md` 7章)
- **利用者の記録(users/sessions/miss_records等)は失われる。** バックアップが無いため復旧手段はない。利用者には「学習用の個人アプリであり、長期的な記録の保持は保証しない」ことをrelease-note.mdで案内している

失効が近づいた場合、有償プランへのアップグレードまたはDBの作り直し(お題マスタは自動復元、記録は消える前提)のいずれかをRenderダッシュボードから手動で行う。
