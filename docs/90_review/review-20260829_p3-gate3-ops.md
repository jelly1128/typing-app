## 重要度A(必須)

### A1. セッション結果の送信が失敗すると、そのセッションの記録が復旧手段なしに失われる

- 対象ファイル・箇所: `sequence.md` 1章(29-42行)・5.1(102-119行)、`class-design.md` 2.4 `sessionStore`(172行)・2.9 未決事項(217行)
- 指摘内容:
  - ADR-002 の設計により、タイピング中(S-03)は一切通信せず、**セッション中の全データ(`correctKeyCount` / `missRecords[]` / `keystrokeIntervalsMs[]` / かな出現回数)は `sessionStore` のメモリ上にしか存在しない**。これが `POST /api/sessions` 1回で初めて永続化される。つまりこのリクエストが単一障害点になっている。
  - 5.1 のエラー系フローは「500 ErrorResponse → エラー表示に切り替え」で終わっており、**再送する手順も、送信できなかった一時ログを保持し続ける規定もない**。フロー図上も `Store→View: エラー表示` で完結しているため、実装者は素直に読むと「エラー画面を出して終わり」を書く。利用者が画面をリロードするか S-02 に戻った時点で、その回の記録は完全に消える。
  - この失敗は例外的事象ではなく**日常的に起きる**。`deployment.md` 2章のとおりバックエンドは Render 無料枠の Web Service で 15 分無通信でスピンダウンし、復帰に約1分かかる。ADR-002 の設計上、セッション開始時のお題取得(S-02)から結果送信(S-04)までは数分空くだけなので必ずしも毎回ではないが、「久しぶりに開いて1本打ち、その1本目を送るときにコールドスタートに当たる」経路は構造的に頻出する。加えてフロント側の通信タイムアウト値がどこにも定義されていないため、`client.ts`(`class-design.md` 2.3)にタイムアウトを実装した場合、コールドスタート復帰(約1分)より短い値を設定すると**正常なサーバーを障害と誤判定して結果を捨てる**。
  - `charter.md` 2章の完了条件は「公開 URL で他人がタイピングでき、記録が DB に残り」である。渡した相手の最初の1本が高確率で消える状態は、完了条件そのものを毀損する。
- 推奨対応:
  - `sequence.md` 5.1 に**再送の分岐を1本足す**。500/ネットワークエラー時は `sessionStore` の一時ログをクリアせずに保持し、S-04 に「もう一度送信する」ボタンを置いて同じ `SessionSubmission` を再 POST する。送信成功で初めて一時ログを破棄する、という順序を明記する(現状は成功時に何をクリアするかも書かれていない)。
  - `client.ts` のタイムアウト方針を `class-design.md` 2.3 に1行決める。**コールドスタートを考慮して 90 秒程度**とするか、タイムアウトを設けずブラウザ既定に任せるかのどちらかを明示する。あわせて「送信中はローディング表示にして二重送信を防ぐ」旨も添える(A1 の再送と `POST /api/sessions` の重複登録防止の両方に効く)。
  - 余力があれば、`sessionStore` の一時ログを送信成功まで localStorage にも退避する(リロード耐性)。これは B 相当の追加なので必須ではないが、実装コストは数行。

### A2. DB が失効・再作成されたときのシードデータ再投入手段が設計に無く、NFR-08 の復旧方針が実行できない

- 対象ファイル・箇所: `db-access.md` 6章末尾(126行「具体的なFlywayマイグレーションファイルへの反映はP5実装時に行う」)、`class-design.md` 1.4 Repository/Entity 一覧、`sequence.md` 2〜4章
- 指摘内容:
  - `nonfunctional-design.md` NFR-08 と `charter.md` 6章は、無料枠 Postgres が 30 日(+猶予 14 日)で失効することを受入リスクとし、**復旧策として「シードデータ/初期状態から作り直す、または無料DBを再作成する」を明示的に採用している**。つまりこのプロジェクトでは、DB の作り直しが例外処理ではなく**想定された正常運用**になっている。
  - ところが、その復旧策の実体である「シードデータをどう再投入するか」は、`table-definition.md` TBL-03 の「シードデータとして開発者が投入する」という一文だけで、P3 の DB アクセス設計である `db-access.md` でも決まっていない。手動 INSERT で投入した場合、**DB を作り直すと `topic_sets` / `sentences` が空になり、再現手段が残らない**。お題が無ければアプリは何もできないため、事実上サービスが復旧不能になる。
  - さらに悪いことに、`topic_sets` が空のときの挙動がどこにも定義されていない。`GET /api/topic-sets` は 404 ではなく **200 + 空配列**を返すため(`sequence.md` にはお題セット取得のフロー自体が無い)、フロントはエラーにもならず「選べるお題が1つも無い S-02」を表示して詰む。5.2 の 404 → S-01 強制遷移のような救済経路にも乗らない。
  - `sessions` / `miss_records` が消えるのは受入済みなので構わないが、**マスタデータ(TBL-02/TBL-03)まで同じ扱いにしてはいけない**。これらは利用者データではなくアプリの一部であり、リポジトリで再現可能であるべきもの。
- 推奨対応:
  - `db-access.md` に「**お題セット・お題文のシードデータは Flyway マイグレーション(`V__` または繰り返し可能な `R__`)としてリポジトリで管理し、DB を新規作成すれば起動時に同じお題が投入される状態にする**」を1〜2行で明記する。分割粒度は P5 でよいが、投入手段が Flyway であることだけは今決める。これで NFR-08 の復旧策が「Render で DB を作り直して環境変数を差し替えるだけ」に確定し、手順書も不要になる。
  - あわせて、Flyway の適用タイミング(Spring Boot 起動時の自動適用=デプロイのたびに適用される)を1行書き添える。Render は再デプロイのたびに起動するため、この前提が共有されていないと「デプロイしたらスキーマが変わっていた/いなかった」が曖昧になる。
  - `topic_sets` が 0 件のときの S-02 表示(「お題がありません」等)を `sequence.md` か `class-design.md` 2.5 に一言。実装は数行だが、これが無いと空画面の原因が利用者にも運用者にも分からない。

## 重要度B(推奨)

### B1. `POST /api/users` の find-or-create は read-then-write なのに「単一の読み書き」として @Transactional 不要と明記されている

- 対象ファイル・箇所: `db-access.md` 5章(115行)、`class-design.md` 1.4 `UserService`(63行)、`table-definition.md` TBL-01 `name UNIQUE`
- 指摘内容: 5章は「他のエンドポイント(GET系、`POST /api/users`のfind-or-create)は**単一の読み書きのみ**のため、明示的な`@Transactional`は付けず…」としているが、find-or-create は `findByName` → 無ければ `save` という**明確な read-then-write の複合操作**であり、記述が事実と合っていない。この記述のまま実装すると、`UserService` に対する 2 リクエストが接近したとき(名前入力ボタンの二重クリック、モバイル/回線状況によるブラウザの自動再送)、両方が `findByName` で空を見て両方 insert し、後発が `users.name` の UNIQUE 制約違反で `DataIntegrityViolationException` → 500 になる。利用者から見ると「名前を入れたらエラーが出て先に進めない」という**アプリの入口で詰まる**症状になり、しかも 1 回リトライすれば通るため再現が難しく、原因究明に時間を使う典型パターン。
- 推奨対応: 5章の記述を「find-or-create は read-then-write のため `@Transactional` を付ける。ただし UNIQUE 制約は同時実行の最終防波堤であり、**制約違反を捕捉したら `findByName` で取り直して既存ユーザーを返す**(競合したもう一方が作った行を採用する)」に改める。実装は try-catch 1つ。トランザクションだけでは(READ COMMITTED では)競合は防げないので、捕捉して取り直す方をセットで書くのが重要。

### B2. `GlobalExceptionHandler` の例外マッピングが自作例外3クラスのみで、Spring が投げる例外の分類が未定義

- 対象ファイル・箇所: `class-design.md` 1.4「例外・エラーハンドリング」(96-102行)、`sequence.md` 5.1(114行「保存失敗(制約違反・DB接続断等)」)
- 指摘内容:
  - 列挙されているのは `UserNotFoundException` / `TopicSetNotFoundException` / `InvalidSessionSubmissionException` の3つだけで、実際の運用でハンドラに到達する例外の大半である Spring 標準例外の扱いが決まっていない。具体的には、Bean Validation 失敗(`MethodArgumentNotValidException`)、不正 JSON / 型不一致(`HttpMessageNotReadableException`)、DB 接続断(`CannotGetJdbcConnectionException` 等)、制約違反(`DataIntegrityViolationException`)。
  - 未マッピングの例外はすべて 500 に落ちるため、`nonfunctional-design.md` NFR-09 が決めた「400(入力値の不正)/404(リソース不在)/5xx(サーバー側障害)」の切り分けが**実装レベルで崩れる**。運用上の実害は、利用者の入力ミスとサーバー障害が同じ 500 として混ざり、NFR-07 で残すことにした 500 ログの中から本物の DB 障害を探せなくなること。個人開発でログ検索の手段が Render のログ画面しかない以上、ここが濁ると診断コストが跳ね上がる。
  - `sequence.md` 5.1 が「制約違反・DB接続断等」を同じ矢印にまとめている点も同様。制約違反はコード/データの不整合(アプリのバグ)、接続断はインフラ事象で、運用者が取るべき次のアクションが違う。
- 推奨対応: `class-design.md` の例外表に「例外 → HTTP ステータス → `ErrorResponse.code`」の対応行を追加し、**未マッピング例外は一律 500 + スタックトレース出力**をフォールバックとして明記する。最低限、上記4種を明示するだけでよい。あわせて `ErrorResponse.code` に入れる文字列の一覧(例: `VALIDATION_ERROR` / `USER_NOT_FOUND` / `INTERNAL_ERROR`)をここで決めると、フロントの `client.ts` が `code` で分岐でき、A1 の再送判定(再送する価値がある失敗か否か)にも使える。

### B3. 404(userId 失効)が発生してもサーバーログに何も残らず、運用側から把握できない

- 対象ファイル・箇所: `class-design.md` 1.4(100行「500時のログ出力(NFR-07)」)、`sequence.md` 5.2(121-142行)
- 指摘内容: `GlobalExceptionHandler` の責務は「**500時**のログ出力」と限定されており、404 はログに残らない設計になっている。一方 5.2 のフローは、404 を受けたフロントが **localStorage をクリアして S-01 へ強制遷移する**、つまり利用者から見れば「履歴が全部消えて名前入力からやり直しになる」という最も重い体験を引き起こす。A2 のとおり DB の作り直しは想定された正常運用なので、この事象は必ず、しかも全利用者に同時に起きる。それがサーバー側に一切記録されないと、「誰かの履歴が消えたらしい」という報告を受けても、いつ何件起きたのかを確認する手段が無い。
- 推奨対応: `GlobalExceptionHandler` の責務に「4xx は WARN で1行(traceId / エンドポイント / userId)を出力する。スタックトレースは不要」を追加する。ログ量は個人利用規模なら無視できる。これで DB 作り直し後の 404 発生を Render のログで確認できる。

### B4. API ベース URL の解決方法が未定義で、環境変数化すると本番だけ通信できない事故になる

- 対象ファイル・箇所: `class-design.md` 2.3 `client.ts`(157行「fetchラッパー。baseURL・共通ヘッダー…を一元化」)
- 指摘内容: `deployment.md` 3章は「Static Site の Rewrite ルールで `/api/*` をバックエンドへプロキシし、ローカルは Vite の `server.proxy` が同じ役割を担う。CORS 設定は行わない」と決めている。この構成では**フロントから見た API のベース URL は local / 本番どちらも `/api` の相対パスで固定でよく、環境差は 0**。ところが `class-design.md` は「baseURL を一元化」としか書いていないため、実装者が素直に `VITE_API_BASE_URL` のようなビルド時環境変数を導入する余地が残っている。そうすると Render Static Site 側にビルド環境変数の設定が必要になり、設定を忘れると**ビルドは通り、デプロイも成功し、本番でだけ localhost:8080 を叩いて全 API が失敗する**。ブラウザコンソールを見れば原因は分かるが、わざわざ環境差を作り込む必要がない場面で作り込むことになる。
- 推奨対応: 2.3 に「**baseURL は `/api` 固定(相対パス)とし、環境変数で切り替えない**。環境差の吸収は本番=Render の Rewrite、local=Vite proxy が担う(`deployment.md` 3章)」と1行明記する。これで環境変数の設定漏れという事故クラスを丸ごと消せる。

### B5. Flyway と JPA Entity のスキーマ二重管理について、どちらが正かが決まっていない

- 対象ファイル・箇所: `db-access.md` 1章(15-18行)・2章 Entity 一覧(29行 `@Table(uniqueConstraints = ...)`)・6章(126行)
- 指摘内容:
  - `db-access.md` は Entity のマッピング(`@ManyToOne`、`@Enumerated`、`@UniqueConstraint`)を設計している一方、実テーブルは Flyway で作る。**どちらがスキーマの正か、`spring.jpa.hibernate.ddl-auto` に何を設定するか**が書かれていない。Spring Boot の既定値は非組込み DB では `none` なので放置しても大事故にはならないが、開発中に「テーブルが無い」という理由で実装者が `update` を入れると、以後 Render へのデプロイのたびに Hibernate が本番スキーマを推測で変更するようになる。`update` はカラム追加はしても削除・型縮小はしないため即座にデータが壊れるわけではないが、Flyway が管理していない列が本番にだけ存在する状態が生まれ、原因追跡が難しくなる。
  - 29行の `@UniqueConstraint` のように、Entity 側にだけ書かれた制約は `ddl-auto: none` では **DDL に反映されない**(Flyway の SQL に同じ制約を書かない限り実在しない)。設計を読んだだけでは「Entity に書いたから効いている」と誤解しうる。
  - `char_type` の CHECK 制約(`table-definition.md` TBL-05)と Java enum 定数の文字列一致も同様に二重管理で、片方だけ増やすと**実行時に制約違反 → 500** になる。
- 推奨対応: `db-access.md` に「**スキーマの正は Flyway。`spring.jpa.hibernate.ddl-auto: none` を local/本番とも固定し、Hibernate に DDL を生成させない**。Entity のアノテーションはマッピング宣言であり、UNIQUE/CHECK/インデックスは 6章の内容も含めてすべて Flyway の DDL に書く」を明記する。3行で済み、以後の事故をまとめて防げる。

### B6. 本番の生死と DB 疎通を切り分ける入口(ヘルスチェック)がクラス設計に存在しない

- 対象ファイル・箇所: `class-design.md` 1.4 Controller 一覧(52-57行)
- 指摘内容: Controller は業務用の4クラスのみで、稼働確認用のエンドポイントが無い。`nonfunctional-design.md` NFR-03 でコールドスタート(復帰まで約1分)を許容している以上、障害時にまず知りたいのは「アプリがまだ起きていないのか」「起きているが DB に繋がっていないのか」だが、現状はその切り分けを業務 API の 500 とログだけで行うことになる。A2 のとおり DB 差し替えが想定運用に入っているため、差し替え直後に疎通だけ確認したい場面も確実に発生する。Render 側にもヘルスチェックパスを設定する欄がある。
- 推奨対応: Spring Boot Actuator の `health` のみ有効化し(`/actuator/health`、DB の up/down を含む)、`class-design.md` の Controller 一覧に「Actuator の health を有効化する(自作 Controller は不要)」と1行添える。導入コストはほぼゼロで、コールドスタート後のウォームアップにも使える。

### B7. 履歴一覧・ミス分析のクエリに件数上限が無く、利用が続くほど線形に重くなる

- 対象ファイル・箇所: `db-access.md` 4.1 `findByUserIdOrderByPlayedAtDesc`(54行)、4.3 拍単位ミス集合クエリ(74-80行)、`sequence.md` 2章・4章
- 指摘内容:
  - 履歴一覧(FR-08)は全件を返す。ミス分析(FR-10)の `DISTINCT ON` クエリは**全期間の全ミス行を Service 層に持ち上げて Java でグルーピングする**設計(4.3)なので、返る行数はプレイ量に比例して無制限に増える。1セッションで数十〜百のミス行が入るため、数百セッションで数万行を1リクエストで JVM に載せることになる。Render 無料枠の Web Service はメモリが小さく、ここが最初に効いてくる箇所になりうる。
  - 個人利用の想定規模なら当面は問題にならないので B とするが、「重くなったときに、どこが原因かをこの設計から思い出せる状態」にはしておきたい。
- 推奨対応: 履歴一覧に上限(直近 100 件など)を入れるのは `findTop100By...` に変えるだけで済むので、今のうちに 4.1 に書いておく。ミス分析は集計を SQL 側(`GROUP BY`)に寄せる余地があるが、4.3 の設計判断(拍単位の重複除去を Service で行う)には合理性があるため、**「全期間集計であり件数無制限である」ことを注記として残す**だけでよい。P8 の振り返りで体感が悪ければ期間を絞る、という申し送りで足りる。

### B8. アドバイス生成の「総出現回数(推定)」の逆算に、ゼロ除算と丸め誤差のリスクがある

- 対象ファイル・箇所: `advice-generation.md` 2章 カテゴリ2(52-55行)、`class-design.md` 1.3 `KanaMissStat`(40行)
- 指摘内容:
  - `総出現回数(推定) = 対象.missCount ÷ (対象.missRate ÷ 100)` という**逆算**をしているが、`missRate` が 0 の場合ゼロ除算になる。Java の double なら `Infinity` になって条件 `>= 5` を素通りし誤ったアドバイスが出る。`BigDecimal` で実装すれば `ArithmeticException` が飛び、B2 のとおり未マッピング例外として 500 になり **S-06(ミス分析画面)が恒久的に開けなくなる**。`byKana` は多い順なので `missRate > 0` のはずだが、`missRate` を表示用に丸めた値として渡す実装にすると 0 が現れうる(丸めのタイミングが `class-design.md` にも `advice-generation.md` にも書かれていない)。丸めた値からの逆算は、そもそも推定値の精度も落ちる。
  - 不自然なのは、`MissAnalysisService`(`db-access.md` 4.3)が**分母である出現回数を実際に持っている**にもかかわらず、`AdviceGenerator` へ渡す `KanaMissStat` からそれを落とし、率から逆算し直している点。同じ表の `CharTypeStat` は `occurrenceCount` を持っている(`class-design.md` 42行)ので、非対称でもある。
- 推奨対応: `KanaMissStat` に `occurrenceCount` を追加し、`advice-generation.md` の逆算をやめて `対象.occurrenceCount >= 5` を直接判定する。record にフィールドを1つ足すだけで、ゼロ除算・丸め誤差・非対称の3つが同時に消える。

### B9. 日本語の enum 定数名がビルド環境の文字エンコーディングに依存する

- 対象ファイル・箇所: `db-access.md` 1章(16-18行「enumはJava enumの定数名をDBのCHECK制約・API仕様のenum値と同じ文字列にする(例: `CharType.清音`)」)
- 指摘内容: 変換テーブルを持たずに済むという判断自体は、この規模では合理的で支持できる。ただし運用面で1点だけ、**ソースファイルの文字コードとコンパイル時のエンコーディング指定に依存する**という副作用が付く。開発は Windows、本番ビルドは `deployment.md` 2章のとおり Docker(`maven:3.9-eclipse-temurin-25`、Linux)で行われるため、Maven の `project.build.sourceEncoding` が未指定だと**ローカルビルドと Docker ビルドで識別子のバイト列が変わりうる**。この種の不具合は「ローカルでは動くのに Render にデプロイすると `char_type` の CHECK 制約違反で 500」という、最も原因が見えにくい形で出る。
- 推奨対応: `db-access.md` の当該箇所に「**この方式の前提として、`pom.xml` に `project.build.sourceEncoding=UTF-8` を設定し、ソースファイルを UTF-8(BOM なし)で保存する**」を注記する。設定1行で前提が固定でき、判断自体を変える必要はない。

### B10. FR-06 の3指標を削る縮小判断が、typing-core / DTO / DB スキーマの3箇所同時変更を要する

- 対象ファイル・箇所: `session-metrics.md` 3章 `SessionResult`(85-92行)、`class-design.md` 1.3 `SessionMetricsResult`(37行)、`table-definition.md` TBL-04(72-75行、`raw_kpm` / `consistency` が NOT NULL)
- 指摘内容: `charter.md` 6章は工数が厳しい場合に **Raw KPM・Consistency・文字種別正解率を先に削減候補とする**と決めている。しかし本設計では `SessionMetricsResult` が4指標すべてを必須フィールドの record として持ち、DB 側も `raw_kpm` / `consistency` が NOT NULL のままである。P2.5 で本番稼働済みの状態からこの削減判断を発動すると、record の変更 + DTO の変更 + 稼働中スキーマへのマイグレーション(NOT NULL 解除)が同時に必要になり、**工数を減らすための判断が追加工数と本番スキーマ変更を生む**構造になっている。
- 推奨対応: 実際に削る判断をした場合は「計算を止めて 0 を保存する(スキーマは触らない)」という逃げ方が最も安く、`session-metrics.md` 4章の判断#3(ゼロ除算時に 0 を入れる方針)とも整合する。**削減時は列を消さず 0 を入れて画面表示だけを止める**、という一文を `session-metrics.md` か `class-design.md` に申し送りとして残せば、判断時に迷わない。設計そのものを今変える必要はない。

## 重要度C(参考)

### C1. `DISTINCT ON` に `ORDER BY` が無く、結果行が非決定的になる

- 対象ファイル・箇所: `db-access.md` 4.3(74-80行)
- 指摘内容: PostgreSQL の `SELECT DISTINCT ON (...)` は、`ORDER BY` が DISTINCT ON の式で始まっていない場合、**グループ内のどの行が採用されるかが不定**と規定されている。本クエリは選択列が `kana` / `prev_kana` / `char_type` で、同一グループ内ではこれらの値も一致するはずなので実害はほぼ無いが、結果の並びが実行のたびに変わりうるため、P4/P6 で結合テストの期待値を書くときに不安定要因になる。
- 推奨対応: `ORDER BY mr.session_id, mr.kana, mr.kana_occurrence_no` を付ける。P5 実装時の申し送りで足りる。

### C2. `GET /best` の呼び出し元が履歴画面だけになっており、縮小判断時に FR-09 の到達性が読み取れない

- 対象ファイル・箇所: `sequence.md` 3章(61-73行、participant が `HistoryView` のみ)、`class-design.md` 2.6 `SessionMetricsSummary.vue`(S-04/S-05 で使用)
- 指摘内容: `charter.md` 6章の縮小判断は「P5 が 8 セッションを超えたら履歴画面(S-05)を切る」。`sequence.md` 3章では自己ベスト取得の呼び出し元が `HistoryView`(S-05)だけなので、この図だけを読むと**S-05 を切ると自己ベスト表示(FR-09)ごと消えるように見える**。実際には `POST /api/sessions` のレスポンスに `isNetKpmBest` / `isAccuracyBest` が含まれるため S-04 での自己ベスト比較は生き残るはずだが、その関係が図から読み取れない。
- 推奨対応: 3章に「S-04 の自己ベスト比較は `POST /api/sessions` のレスポンスのフラグで行うため、S-05 を切っても FR-09 の表示は失われない」と1行注記する。縮小判断を実際に下すときに迷わなくなる。

### C3. `traceId` を利用者に見せる責務が、フロントエンドのクラス設計に現れていない

- 対象ファイル・箇所: `class-design.md` 2.3 `client.ts`(157行)、`sequence.md` 5.1(116-118行)
- 指摘内容: `nonfunctional-design.md` NFR-07 では `traceId` を「レスポンスとログの双方に同じ値を出す」と決めており、これは問い合わせを受けたときにログと突き合わせる鍵になる。しかしフロント側は `ErrorResponse` を「パースする」までしか設計されておらず、**エラー画面に `traceId` を出す責務がどこにも割り当てられていない**。公開 URL を他人に渡す前提(`charter.md` 2章)では、「エラーが出た」という報告に `traceId` が添えられているかどうかで調査コストが大きく変わる。
- 推奨対応: エラー表示コンポーネントに `traceId` を小さく併記する(「エラーコード: xxxx」程度で十分)。P5 実装時の申し送りで足りる。

### C4. Render のログ保持と DB 接続タイムアウトは、実装時に値を1度だけ確認しておく

- 対象ファイル・箇所: `db-access.md` 5章、`class-design.md` 1.4
- 指摘内容: Render のログは無期限には残らないため、障害報告を受けてから日を空けて見に行くと消えている可能性がある。また HikariCP の `connection-timeout` 既定値(30 秒)は、Render Postgres 側の状態によっては A1 のコールドスタートと重なって体感待ち時間を伸ばす。どちらも設計を変える話ではなく、**「気付いたその場でログを見る」「タイムアウト値は既定のままにする(明示的に短くしない)」という前提を持っておく**だけでよい。監視基盤の追加は不要(現行方針が妥当)。
- 推奨対応: P7 の `operation.md` に1行ずつ残す。

## 観点別の総括

- **障害時の挙動**: NFR-09 の 400/404/5xx 方針を `sequence.md` 5.1/5.2 が具体的なフローに落としており、**エラー系フローが図として存在する**こと自体が P2 からの明確な前進。特に 5.2 の「404 → localStorage クリア → S-01 強制遷移」を全 View 共通の発火経路として書いた点は、実装時に迷わない粒度になっている。一方で、5.1 が「エラー表示に切り替え」で終わっていて**その先(再送)が無い**ため、コールドスタートという確実に起きる事象でデータが失われる(A1)。また例外→ステータスの対応表が自作例外3つ分しかなく、実運用でハンドラに来る例外の大半が未定義のまま 500 に落ちる(B2)。この2点を埋めれば、障害時の挙動としては個人開発規模に十分見合う。
- **環境差異の吸収**: `deployment.md` 3章の Rewrite / Vite proxy による「同じ設計を2つの機構で再現する」構成は、CORS と API URL という最も差が出やすい2項目を設計レベルで消しており、この規模では理想的。詳細設計側で残っているのは、その前提が `client.ts` に伝わっておらず環境変数化の余地が残っている点(B4)、`ddl-auto` の固定が明記されていない点(B5)、日本語 enum のソースエンコーディング依存(B9)の3つ。いずれも設定1行の明記で閉じる。
- **データの安全性**: セッション保存を1トランザクションにまとめ部分保存しない(`db-access.md` 5章)、削除・更新の API が1本も無い、中断セッションは行を作らない、という構成により**利用者操作でデータが壊れる経路が塞がれている**点は引き続き良い。危ういのは2箇所で、(1) 永続化前の一時ログが単一の POST に賭けられており失敗時の復旧手段が無いこと(A1)、(2) DB 作り直しが想定運用なのにマスタデータの再現手段が決まっていないこと(A2)。どちらも「取り消し手段が無い操作」ではなく「復旧手段が無い喪失」なので、A に置いた。find-or-create の競合(B1)も同系統だがリトライで回復するため B とした。
- **監視・診断のしやすさ**: NFR-07 のログ必須項目が P2 で確定しており、`GlobalExceptionHandler` に `traceId` 採番とログ出力の責務が明示されている(`class-design.md` 1.4)ので、骨格は出来ている。APM を入れないという割り切りも1人運用として正しい。不足しているのは、4xx が一切ログに残らないこと(B3)、アプリの生死と DB 疎通を切り分ける入口が無いこと(B6)、`traceId` を利用者に見せる出口が無いこと(C3)。3点とも数行の追加で、監視基盤の増設は不要。
- **リスク対策の実現性**: `charter.md` 6章のうち「P2.5 で先に本番へ出す」は既に達成済み(`deployment.md` 7章)、「履歴画面を切る」も `POST /api/sessions` のレスポンスに自己ベストフラグを含む設計のおかげで FR-09 を巻き添えにせず切れる(C2 で図に注記すれば十分)。`advice-generation.md` が3カテゴリを独立判定する構造になっているため、文字種別正解率を削っても他2カテゴリが動く点も、縮小判断と素直に噛み合っている。矛盾が残るのは「FR-06 の3指標を先に削減候補とする」で、record と NOT NULL カラムにより削減判断が3箇所同時変更を誘発する(B10)。ただしこれは「0 を保存して表示だけ止める」という申し送りを1行残せば実質解消できるため、B に留めた。
