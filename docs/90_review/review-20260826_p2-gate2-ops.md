## 重要度A(必須)

### A1. エラー応答の中身とログ出力の責務が設計に無く、本番で「500 が出た」以上の情報が取れない

- 対象ファイル・箇所: `api-spec.yaml` `components.responses.ServerError`(197-198行)、`nonfunctional-design.md` NFR-07(41-43行)・NFR-09(49-53行)、`system-architecture.md` 6章 NFR-07 行
- 指摘内容:
  - `ServerError` は `description` だけで `content`(レスポンスボディのスキーマ)が定義されていない。全7エンドポイントがこれを共通参照しているため、**500 応答のボディが何であるかが全 API で未定義**になっている。フロントエンドは「HTTP ステータスが 500 か」以外に手掛かりが無く、画面側のエラー分岐が実装者の場当たりで決まる。
  - NFR-07 は「Logback デフォルトで起動・未処理例外をログ出力する」とあるだけで、**500 を返すときに何をログに残すか**(発生したエンドポイント、userId / topicSetId 等の入力値、リクエストを一意に識別する ID、例外の分類)が決まっていない。NFR-09 は「一様に 5xx を返す」と決めているが、一様にすると個々の 500 の原因(DB接続断/FK違反/バリデーション超過/NPE)がログでしか区別できず、そのログの中身が未定義という状態になっている。
  - Render 無料枠はスリープ・コールドスタートがあり(NFR-03)、他人に公開 URL を渡す(charter 2章)。「使ったら赤いエラーが出た」という報告だけが届き、再現できないまま原因不明になる典型パターンにはまる。
  - 加えて、例外をどこで捕まえて 500 に変換するか(`@RestControllerAdvice` 等の一元的なハンドラを置くか、各 Controller で個別に処理するか)が決まっていないため、実装者ごとにログの出方が変わり、後から検索できないログが本番に残る。
- 推奨対応:
  - `api-spec.yaml` に共通エラーボディのスキーマを1つ追加する(例: `ErrorResponse { timestamp, status, code, message, traceId }`)。`traceId` は問い合わせを受けたときにログと突き合わせる鍵になるので、画面にも表示できる形にしておく。
  - 例外→HTTPステータス→ログ出力を一元化する方針(例外ハンドラを1箇所に置く)を BD-006 に1段落で書く。詳細なクラス設計は P3 でよい。
  - ログに必ず残す項目を NFR-07 に明記する(最低限: 発生時刻、エンドポイント + HTTPメソッド、`traceId`、userId、例外クラス名、スタックトレース)。個人開発なので APM は不要という現行方針は妥当で、変える必要はない。
- **対応状況(2026-08-26, P2-07)**: クローズ。`api-spec.yaml` に `ErrorResponse`(timestamp/status/code/message/traceId)を追加し `ServerError`/`BadRequest`/`NotFound` すべてに適用。`system-architecture.md` に `@RestControllerAdvice` 一元化の方針を追記。`nonfunctional-design.md` NFR-07 にログ必須項目を列挙した

### A2. NFR-08 が「Render 標準バックアップに委ねる」としているが、無料枠でそれが提供される前提が未検証のまま設計の土台になっている

- 対象ファイル・箇所: `nonfunctional-design.md` NFR-08(45-47行)、`system-architecture.md` 6章 NFR-08 行
- 指摘内容:
  - NFR-08 は「Render Managed PostgreSQL の標準バックアップ機能に委ねる。世代数・保持期間は Render のプラン仕様に従う。リストア手順の個別マニュアル化は行わない」とだけ書かれている。しかし charter 5章の制約は「Render 無料枠の範囲で収める」であり、**無料プランの Managed Postgres でバックアップ(スナップショット/PITR)が提供されるか、インスタンス自体に有効期限があって期限後に削除されるかは、プラン仕様に強く依存する**。この設計はその確認を一切していない状態で「委ねる」と宣言しており、実際には何もバックアップされていない可能性がある。
  - これが外れると、charter 2章の完了条件「記録が DB に残り」が本番で満たせなくなる。テーブル定義には削除機能もソフトデリートも無いため、DB ごと消えた場合の復旧手段がゼロになる(お題のシードデータも消えるのでアプリ自体が空になる。B2 も参照)。
  - 「リストア手順の詳細化・訓練は行わない」という判断自体は個人開発として妥当だが、**バックアップが存在するかどうかの確認は判断以前の事実確認**であり、これを済ませないまま P2.5 で本番へ出すと、消えてから気付くことになる。
- 推奨対応:
  - P2.5(Walking Skeleton)着手時に、使う Render プランの Postgres について「自動バックアップの有無」「インスタンスの有効期限の有無」の2点だけ実際のダッシュボードで確認する。確認は5分で済む。
  - 結果に応じて NFR-08 を次のいずれかに書き換える:
    (a) バックアップがある → 保持期間を明記し現行方針を維持
    (b) 無い → `pg_dump` を手動で取る(節目のみで可)手順を1行でも REL-002 `operation.md` に残す
    (c) 取らない → 「本番データは消えうる。消えたらシードから作り直す」ことを受入リスクとして charter 6章に追記する
  - どれを選んでも工数はほぼ増えない。**未確認のまま「委ねる」と書いてある状態だけが危険**。
- **対応状況(2026-08-26, P2-07)**: P2時点ではクローズせず、P2.5着手時タスクとして`wbs.md`に明記(実際のRenderダッシュボード確認が必要なため設計書の記述だけでは閉じられない)。`nonfunctional-design.md` NFR-08 は「P2.5で確認し(a)(b)(c)いずれかを選ぶ」という決定待ち状態に改訂済み

### A3. localStorage の userId が本番 DB と食い違ったとき、利用者が自力で復旧できない

- 対象ファイル・箇所: `screen-design.md` 2章(41行)・S-02(54-62行)、`api-spec.yaml` `POST /api/sessions`(87-112行)・`GET /api/users/{userId}/sessions`(114-136行)、`table-definition.md` TBL-04(70行 FK→users)
- 指摘内容:
  - 画面設計では「userId と名前を localStorage に保存し、値があれば S-02 から始める。値が無い場合のみ S-01 を経由する」と決めている。つまり **S-01(名前入力)へ戻る導線が、localStorage を消す以外に存在しない**。S-02 の表示項目も「現在の名前」だけで、名前を変える操作は用意されていない。
  - 一方 DB 側は、開発中の作り直し・Flyway でのスキーマ再構築・無料枠 DB の再作成(A2)など、**users テーブルが空になる事象が現実的に起きる**。そのとき既存ブラウザの localStorage には古い userId が残る。
  - この状態で何が起きるかというと、`POST /api/sessions` は FK 違反で 500(api-spec に 404 も 400 も定義が無いため、NFR-09 の方針どおり一様に 500)、`GET /api/users/{userId}/sessions` は存在しないユーザーとして空配列 200 が返る。**利用者から見ると「履歴が全部消え、練習しても毎回エラーになり、直す方法が無い」**という状態に固定される。ブラウザの開発者ツールで localStorage を消せる人しか復旧できない。
  - charter の目的3は「公開 URL を他人に渡せる」ことなので、渡した相手がこの状態に落ちると、こちらから復旧させる手段が無い。
- 推奨対応:
  - `api-spec.yaml` の userId を受け取る4エンドポイント(`POST /api/sessions`、`GET /api/users/{userId}/sessions`、`/best`、`/miss-analysis`)に **404(該当ユーザーが存在しない)を定義**し、500(サーバー側障害)と切り分ける。
  - `screen-design.md` に「userId 系 API が 404 を返したら localStorage をクリアして S-01 に戻す」挙動を追記する。実装は数行で済む一方、これが無いと詰みになる。
  - 併せて S-02 に「別の名前で始める(名前を変更する)」導線を常設する。他人に URL を渡したとき、その人が自分の名前で始める入口にもなり、A3 とは別に運用上あった方がよい。
- **対応状況(2026-08-26, P2-07)**: クローズ。`api-spec.yaml` のuserId系4エンドポイントに404を追加し500と切り分け。`screen-design.md` に「404受信時はlocalStorageをクリアしS-01へ」の挙動と、S-02の「別の名前で始める」導線を追記した

## 重要度B(推奨)

### B1. フロントエンドの配信方式が決まっておらず、CORS と API ベース URL の扱いが宙に浮いている

- 対象ファイル・箇所: `system-architecture.md` 1章 全体構成図(11-19行)・4章(46-53行)、`nonfunctional-design.md` NFR-04(27-29行)
- 指摘内容: NFR-04 は「フロントエンド→バックエンドの通信も同じ公開 URL 配下で HTTPS になる」と書いており same-origin を暗に前提にしているが、構成図と 4章のモジュール構成では frontend/ が独立モジュールになっており、**Render の Static Site として別ドメインに置くのか、Spring Boot の静的リソースに同梱して1サービスで配信するのかが決まっていない**。前者なら CORS 許可設定が必須で、後者なら不要。ローカル開発では Vite dev server(別ポート)とバックエンドが必ず別オリジンになるため、いずれにせよ開発時だけ CORS かプロキシ設定が要る。ここが未定のまま P2.5 に入ると、Walking Skeleton の最初のブロッカーになる(症状はブラウザコンソールに出るので原因不明にはならないため B とする)。API ベース URL(local: `http://localhost:8080` / 本番: Render の URL)をビルド時環境変数(`VITE_` 接頭辞)で切り替える方針も同様に未記載。
- 推奨対応: BD-007 `deployment.md`(台帳では未着手)で「1サービス同梱 or 2サービス分離」を先に決め、決めた側に応じて CORS 許可オリジンと API ベース URL の環境変数を明記する。NFR-06 が扱っているのは DB 接続情報だけなので、この2つも環境変数の対象として NFR-06 に足しておく。

### B2. Flyway の運用方針(適用タイミング・破壊的変更・シードデータ)が「P5 で決める」のまま

- 対象ファイル・箇所: `table-definition.md` 未決事項(116-120行)、TBL-03 の注記(61行)、`system-architecture.md` 3章 DB 行
- 指摘内容:
  - 未決事項は「Flyway のマイグレーションファイル分割は P5 実装時に決める」のみで、運用上重要な次の3点が抜けている。
    1. **適用タイミング**: アプリ起動時に自動適用するのか、手動で流すのか。Render は再デプロイのたびに起動するため、自動適用ならデプロイ = スキーマ変更になる。方針が無いと「デプロイしたらスキーマが変わっていた/変わっていなかった」が曖昧になる。
    2. **破壊的変更の扱い**: Flyway Community には undo が無い。カラム削除・型縮小・NOT NULL 追加は一方通行で、既存データを壊す。「既存カラムは削除・型変更せず、追加→移行→(必要なら)後日削除の段階適用にする」という原則を1行決めておくだけで、本番データを壊す事故は大半防げる。`flyway.clean` を本番で無効にすることも明記したい。
    3. **シードデータ**: TBL-03 は「シードデータとして開発者が投入する」とあるだけで、投入手段が未定義。**手動 INSERT にすると DB を作り直したときにお題を再現できず、アプリが空で使えなくなる**(A2 と直結)。お題は Flyway のマイグレーション(またはリポジトリ内の SQL ファイル)としてバージョン管理し、DB を作り直せば同じお題が入る状態にしておくべき。
- 推奨対応: 上記3点を BD-006 か BD-007 に数行で追記する。分割粒度は P5 でよいが、この3点は本番へ出す前に決めておく性質のもの。

### B3. 本番の稼働確認・DB 疎通確認の入口が無い

- 対象ファイル・箇所: `nonfunctional-design.md` NFR-03(23-25行)・NFR-07、`api-spec.yaml` paths 全体
- 指摘内容: API は業務用の7本のみで、**ヘルスチェック用のエンドポイントが無い**。NFR-03 でコールドスタートを許容している以上、「アプリが起きているのか」「起きているが DB に繋がっていないのか」を切り分ける手段が要る。これが無いと、A1 の 500 が出たときにアプリ側の問題か DB 側の問題かをログだけで判断することになる。Render 側もヘルスチェックパスを設定できる。
- 推奨対応: `/actuator/health`(Spring Boot Actuator の health のみ有効化、DB の up/down を含む)を1つ足し、api-spec か BD-007 に記載する。導入コストはほぼゼロで、コールドスタート後のウォームアップ確認にも使える。

### B4. 本番データを直接見る/直す手段が設計に含まれていない

- 対象ファイル・箇所: `table-definition.md` 全体、`nonfunctional-design.md` NFR-08
- 指摘内容: アプリには削除・編集の機能が一切なく(これ自体は誤操作によるデータ消失が起きない良い設計)、その裏返しとして**入ってしまったデータを消す手段がアプリ側に存在しない**。公開 URL を他人に渡す前提(charter 目的3)では、他人のテスト記録が users / sessions に混ざる、テスト中の異常値が自己ベスト(FR-09)を占有する、といったことが普通に起きる。そのとき本番 DB に psql で繋いで消す以外の方法が無いが、その接続手段(Render の External Connection 情報をどこから取るか、ローカルからの接続可否)が設計にも運用手順にも書かれていない。診断のためにテーブルを覗く用途でも同じ手段が要る。
- 推奨対応: BD-007 か REL-002 `operation.md` に「本番 DB への接続方法」を3行程度で残す(接続文字列の取得場所、psql コマンド、注意点)。UI での削除機能追加は不要(スコープ外の方針を変える必要はない)。

### B5. charter 6章「3指標を削減候補にする」判断を、この設計のまま実行するとスキーマと API の変更が必要になる

- 対象ファイル・箇所: `table-definition.md` TBL-04(72-75行 `raw_kpm` / `consistency` が NOT NULL)、`api-spec.yaml` `SessionSubmission.required`(268行に `keystrokeIntervalsMs` を含む)、charter 6章「実装が膨らんで工程が終わらない」行
- 指摘内容: charter は工数が厳しい場合に Raw KPM・Consistency・文字種別正解率を先に削ると決めている。しかし本設計では `raw_kpm` / `consistency` が **NOT NULL** で、Consistency 算出の入力 `keystrokeIntervalsMs` が **required** になっている。P2.5 で Walking Skeleton を本番に出した後にこの削減判断を発動すると、「NOT NULL カラムに何を入れるか」問題が発生し、本番稼働中のスキーマ変更(B2 の破壊的変更)と API スキーマ変更が同時に必要になる。つまり、**工数を減らすための判断が逆に追加工数を生む**構造になっている。
- 推奨対応: 削減候補の3指標に対応する `raw_kpm` / `consistency` を **NULL 許容**にし、`keystrokeIntervalsMs` を required から外す(送らない場合 consistency は null)。基本3指標(Net KPM・正確率・所要時間)は NOT NULL のままでよい。これだけで、削減判断をしても DB スキーマにも API 契約にも手を入れずに済む。

### B6. 入力起因のエラー(400)が定義されておらず、すべて 500 に落ちてログが濁る

- 対象ファイル・箇所: `api-spec.yaml` 各パスの responses、`POST /api/users`(20-40行)、`POST /api/sessions`(98-112行)
- 指摘内容: 定義されている非 200 応答は `listSentences` の 404 と共通 500 だけ。`POST /api/users` は `maxLength: 100` を schema で宣言しているが、**それを超えたとき何を返すかが未定義**で、そのまま DB へ流れれば `VARCHAR(100)` 制約違反で 500 になる。`POST /api/sessions` も、`enum` 外の `endConditionType`、負の `durationSeconds`、存在しない `topicSetId` がすべて 500 になりうる。運用上の問題は、**利用者入力のミスとサーバー障害が同じ 500 として混ざり、A1 のログで本物の DB 障害を探せなくなる**こと。NFR-09 の「一様に 5xx」は DB 接続断についての方針であり、入力起因の失敗まで含める意図ではないはず。
- 推奨対応: `POST /api/users` と `POST /api/sessions` に 400 を定義し、Bean Validation で弾く方針を BD-006 に1行書く(A1 の共通エラーボディを流用すればよい)。存在しない `topicSetId` / `userId` は 404(A3 と共通)。

## 重要度C(参考)

### C1. 環境変数の一覧を1つの表にまとめておく

- 対象ファイル・箇所: `nonfunctional-design.md` NFR-06(37-39行)
- 指摘内容: NFR-06 は「DB接続URL・ユーザー名・パスワード」だけを挙げているが、実際に local と Render で差が出るのはこれ以外にもある(`PORT`、API ベース URL、CORS 許可オリジン、Flyway の自動適用フラグ、ログレベル)。散らばったまま実装すると、片方の環境にだけ設定漏れが起きて原因究明に時間を使う。
- 推奨対応: BD-007 に「変数名 / local の値 / 本番の値 / 必須か」の4列の表を1つ作る。P3 以降の申し送りで十分。

### C2. Render のログ保持は永続前提にしない

- 対象ファイル・箇所: `nonfunctional-design.md` NFR-07
- 指摘内容: Render のログはプランに応じて保持期間が限られる。障害報告を受けてから数日後に見に行っても残っていない可能性がある。個人開発でログ基盤を建てる必要は無い(現行方針で妥当)が、「気付いたらその場で見る」「重要なスタックトレースは手元にコピーする」という前提だけ意識しておくとよい。
- 推奨対応: REL-002 `operation.md` に「障害時にまずログを確認する」旨を1行。監視基盤の追加は不要。

### C3. charter「履歴画面を切る」の切る対象を明示しておく

- 対象ファイル・箇所: charter 6章、`screen-design.md` 2章(40行)、`api-spec.yaml` `/api/users/{userId}/best`
- 指摘内容: 縮小判断で S-05 を切っても、S-02 ヘッダーから S-06 へ直接遷移できる設計になっているためミス分析には到達できる(この点は整合が取れている)。ただし `GET /api/users/{userId}/best` は S-04 の自己ベスト比較でも使うため **API とテーブルは残す**必要がある。「切るのは画面のみ」と一言添えておくと、判断時に迷わない。
- 推奨対応: BD-002 5章の未決事項に1行追記(実装時の申し送りで足りる)。

### C4. TBL-04 `consistency` の桁数は、本番へ出す前に確定させると後が楽

- 対象ファイル・箇所: `table-definition.md` 未決事項(120行)、`api-spec.yaml` `SessionResult.consistency`(317行)
- 指摘内容: 桁数が「P3 で再確認」の暫定値のまま P2.5 で本番へ出すと、P3 で統計量(標準偏差[ms] か変動係数か)が変わったときに稼働中のスキーマへ型変更マイグレーションが要る。`NUMERIC(8,2)` は拡張方向なら無害だが、縮小や単位変更は既存行に影響する。
- 推奨対応: P2.5 の Walking Skeleton では sessions への保存経路だけ通し、consistency は P3 確定後に本番投入する順序にする、または最初から余裕のある桁で固定する。B5 の NULL 許容化と併せて対応すると自然。

## 観点別の総括

- **障害時の挙動**: NFR-09 で「DB接続断は個別フォールバックを作らず一様に 5xx、フロントは汎用エラー表示」と方針が定まっており、各画面(S-02/S-04/S-05/S-06)の備考にも漏れなく反映されている。この一貫性は良い。ただし 5xx の中身(A1)と、5xx 以外の失敗系である 404/400(A3・B6)が欠けており、「500 が出るがなぜかは分からない」「入力ミスとサーバー障害が区別できない」状態になる。ここを埋めれば方針としては個人開発規模に十分見合う。
- **環境差異の吸収**: NFR-06 で DB 接続情報のハードコード禁止と local(Docker Compose / .env)・本番(Render 環境変数)の使い分けが明記されており、方向性は正しい。一方でフロントエンドの配信方式が未確定なため、CORS と API ベース URL という**環境差が最も出やすい2項目**が設計の外にある(B1)。BD-007 未着手が原因なので、P2.5 の入口で埋めれば足りる。
- **データの安全性**: アプリに削除・更新機能が存在せず(履歴削除UIなし)、セッション保存は1トランザクションで部分保存しない(NFR-09 / TBL-04)、中断セッションは行を作らない、と**利用者操作でデータが壊れる経路が塞がれている**点は評価できる。危ういのは DB そのものの保全で、バックアップが実在するかの確認が未実施(A2)、スキーマ変更の破壊的操作に関する原則とシードデータの再現手段が未定(B2)。この2つは工数ではなく確認と1行の方針で解決する。
- **監視・診断のしやすさ**: 「APM は導入しない」という割り切りは1人運用として正しく、過剰な監視基盤は不要。ただし現状は「Logback デフォルト」以上の記述が無く、障害時に何を見れば原因が分かるかが定義されていない(A1)。加えて、アプリの生死と DB 疎通を切り分ける入口も無い(B3)。ログに残す項目の列挙とヘルスチェック1本の追加で、個人開発規模の診断性としては十分になる。
- **リスク対策の実現性**: charter 6章のうち「P2.5 で Walking Skeleton を先に本番へ出す」は、この設計なら users + topic_sets/sentences + sessions の最小経路で成立し、技術的な矛盾は無い。「履歴画面を切って P6 へ進む」も S-02 → S-06 の直接導線があるため成立する(C3 に補足)。矛盾があるのは「FR-06 の3指標を先に削減候補とする」で、`raw_kpm` / `consistency` の NOT NULL と `keystrokeIntervalsMs` の required により、削減判断がスキーマ・API 変更を誘発する(B5)。ここは NULL 許容化・optional 化という設計上の小さな変更で解消できる。
