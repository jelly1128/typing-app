# テスト可能性レビュー(2026-08-26)

対象:

- `docs/20_basic-design/system-architecture.md`(BD-001)
- `docs/20_basic-design/screen-design.md`(BD-002)
- `docs/20_basic-design/api-spec.yaml`(BD-003)
- `docs/20_basic-design/er-diagram.md`(BD-004)
- `docs/20_basic-design/table-definition.md`(BD-005)
- `docs/20_basic-design/nonfunctional-design.md`(BD-006)

前提: P3(詳細設計)は P4(テスト設計)より前工程であるため、「P3 で確定する」と**明記されている**未決事項(FR-02 の受理表、FR-06 の算出式細部、FR-11 のアドバイス生成ロジック)は、P4 時点では解決済みとみなして本レビューでは A 指摘としない。問題にするのは「どの工程で決まるかが書かれていないまま曖昧に残っている」項目に限る。

## 重要度A(必須)

### A1. ミス記録の `expectedKey` の決定規則が未定義で、FR-10(2) の期待値が一意に決まらない

- 対象ファイル・箇所: `api-spec.yaml` `MissRecordInput.expectedKey` / `table-definition.md` TBL-05 `expected_key VARCHAR(10)`
- 指摘内容: FR-02 は同一のかな1拍に対して複数のローマ字表記を正解として許容する(し=si/shi/ci)。この前提では、ミス発生時点の「期待していたキー」が**一意に定まらない**。例えばかな「し」の先頭で `x` を打った場合、期待キーは `s` なのか `c` なのか、あるいは `si`/`shi` のような表記全体なのか、設計書のどこにも書かれていない(`VARCHAR(10)` という桁数は複数文字を想定しているようにも読めるが、FR-02/FR-03 の判定単位は「ローマ字1キー」と requirements.md 0章で確定している)。さらに `s` まで打った後に `x` を打った場合の期待キーは `i` と `h` の2通りが正解であり、どちらを記録するかも不明。
  この結果、次のテストケースが書けない。
  - FR-04: 「かな『し』の1打鍵目で `x` を入力 → `miss_records` に (expected_key=?, actual_key=x) が1行入る」— 期待値を確定できない。
  - FR-10(2): 「誤りパターン(期待キー→実際キー)別の発生回数」の集計結果を検証できない。同じ誤打鍵が実装次第で `s→x` にも `c→x` にも `si→x` にもなり、テストの合否が実装に依存する。
- 推奨対応: 「複数の受理候補があるとき `expectedKey` に何を記録するか」の規則を P2 で決める(例: 受理候補のうち P3 受理表で定義する代表表記の次の1キーを記録する / 候補を区切り文字で連結して記録する のいずれか)。決められない場合でも、**P3 `logic-spec/romaji-automaton.md` で確定する未決事項として明記**し、桁数 `VARCHAR(10)` の根拠と合わせて申し送ること。
- **対応状況(2026-08-26, P2-07)**: クローズ(P3送りとして明記)。`api-spec.yaml` の `expectedKey` description と `table-definition.md` 未決事項に「P3 `logic-spec/romaji-automaton.md` の受理表確定と合わせて定める」旨を明記した

### A2. API に入力値域・バリデーションと 4xx 応答の定義が一切なく、異常系テストが書けない

- 対象ファイル・箇所: `api-spec.yaml` 全エンドポイント(`responses` が `200/201` と `500`、`listSentences` の `404` のみ)
- 指摘内容: 全 7 エンドポイントを通じて、不正リクエストに対する応答(400 系)が1つも定義されていない。`components/responses` にも `ServerError` しかない。具体的に期待値が書けないケース:
  - FR-12(`POST /api/users`): `name` が空文字・空白のみ・101文字・前後空白付きのとき何が返るか未定義。schema に `minLength/maxLength` はあるが、違反時の**応答**が定義されていないため「400 が返る」とも「500 が返る」とも書けない。また TBL-01 `name` は `UNIQUE` だが、前後の空白や大文字小文字を正規化するかが未定義で、「" Kazuki" と "Kazuki" は同一人物か」というテストの期待値が決まらない(FR-12 の受け入れ条件「同じ名前を入力した場合、同一人物」の判定基準が不定)。
  - FR-05(`POST /api/sessions`): `endConditionValue` に値域制約がない。`0`、負値、極端に大きい値を送ったときの挙動が未定義。S-02 の選択肢(お題 N 文の N の候補、制限時間の候補)も screen-design.md に列挙されていないため、**境界値テストの境界そのものが決まらない**。
  - FR-06(`POST /api/sessions`): `durationSeconds=0`、`correctKeyCount=0 かつ missRecords=[]`、`keystrokeIntervalsMs=[]` または要素1件、といった 0 除算・統計量算出不能になる入力を、API が拒否する(400)のか受理して算出する(その場合の値は?)のかが未定義。requirements.md FR-06 の未決事項は「算出式の細部」を P3 に送っているが、**入力の値域チェックはコントローラ層の責務であり P3 logic-spec の対象外**であるため、現状どの工程でも決まらない。
  - FR-07/FR-10: `missRecords[].kana` が `kanaCounts` に含まれない(分母が存在しない)不整合なリクエストを受理するかが未定義。受理した場合、FR-10(1) の `missRate` は 0 除算になる。
- 推奨対応: `api-spec.yaml` に `BadRequest`(400)応答を共通定義として追加し、各エンドポイントの「不正入力とみなす条件」を列挙する。特に (a) `name` の正規化規則(trim の有無・大文字小文字の扱い)、(b) `endConditionValue` の値域と S-02 の選択肢、(c) `POST /api/sessions` の必須整合条件(`durationSeconds >= 1`、`kanaCounts` と `missRecords` の突き合わせ)を明記する。
- **対応状況(2026-08-26, P2-07)**: クローズ。`api-spec.yaml` に `BadRequest`(400)/`NotFound`(404)/`ErrorResponse` を追加し、`POST /api/users`(name trim規則)・`POST /api/sessions`(endConditionValue値域1〜50/10〜600、kanaCounts整合)・userId系4エンドポイント(404)に適用した。S-02 の具体的な選択肢(N文の候補等)はビジュアル要素としてP3以降に残す(値域自体はAPI側で定義済み)

### A3. 自己ベスト更新(`isNewBest`)の判定基準が未定義で、FR-09 のテストケースが書けない

- 対象ファイル・箇所: `api-spec.yaml` `SessionResult.isNewBest` / `screen-design.md` S-04「自己ベスト比較(この難易度の自己ベストと比較し、更新していれば強調表示)」
- 指摘内容: FR-09 の自己ベストは **Net KPM 最大と正確率最大の2指標**(requirements.md 3章の決定事項)であるのに対し、`isNewBest` は boolean が1つしかなく、どちらの指標の更新を指すのかが定義されていない。
  - Net KPM だけ更新した場合 → true?
  - 正確率だけ更新した場合 → true?
  - 両方更新した場合のみ true?
  - 前回ベストと**同値**だった場合(更新なし・タイ)は true か false か?
  この4パターンすべてで期待値が確定せず、FR-09 の主要テストケース(自己ベスト更新判定)が書けない。S-04 の「更新していれば強調表示」も、どの数値を強調するのかが決まらないため画面テストも書けない。
- 推奨対応: `isNewBest` を指標別(`isNetKpmBest` / `isAccuracyBest`)に分割するか、`isNewBest` の定義を「いずれか一方でも厳密に上回った場合 true(同値は false)」のように文言で確定させる。screen-design.md S-04 の強調表示対象も、その定義に合わせて記述する。
- **対応状況(2026-08-26, P2-07)**: クローズ。`api-spec.yaml` を `isNetKpmBest`/`isAccuracyBest` に分割し(同値はfalse、初回はtrue)、`screen-design.md` S-04 の強調表示対象を対応させた

## 重要度B(推奨)

### B1. NFR-01(50ms)の計測区間・統計処理・合格基準が未定義

- 対象ファイル・箇所: `nonfunctional-design.md` NFR-01「検証方法: ブラウザ開発者ツールの Performance タブ、または簡易な計測用ログで確認する」
- 指摘内容: ツール名はあるが、(a) 計測の始点(`keydown` イベント発火時刻か、キーの物理押下か)と終点(Vue の状態更新完了か、DOM 更新完了か、ペイント完了か)、(b) 何回試行してどう集約するか(最大値・平均・95パーセンタイル)、(c) 測定環境(端末・ブラウザ・他タブの有無)が定義されていない。「50ms 以内であること」というテストケースは書けるが、**合否を一意に判定できない**ため、テスト設計者が独自に基準を決めることになる。
- 推奨対応: 「`keydown` ハンドラ開始から `nextTick` 後の DOM 更新完了まで」のように計測区間を1つに固定し、「連続 100 打鍵の最大値が 50ms 以内」等の合否条件を書き添える。

### B2. NFR-02(体感2秒)の測定条件、特にコールドスタート除外の判定方法が未定義

- 対象ファイル・箇所: `nonfunctional-design.md` NFR-02「例外: Render 無料枠のコールドスタート発生時は2秒を超えうる。これは許容する」
- 指摘内容: 除外条件が「コールドスタート発生時」とされているが、テスト実行中にそれが起きたことを**どう判定するか**が書かれていない。判定方法がないと、2秒超過したテストを「不合格」とすべきか「コールドスタートのため除外」とすべきかがテスト実施者の裁量になり、結果が再現しない。計測対象区間(画面遷移操作からデータ描画完了までか、API 応答時間か)も未定義。
- 推奨対応: 「事前にウォームアップリクエストを1回送り、2回目以降を計測対象とする」等の手順を NFR-02 に追記する。

### B3. お題の出題順・再利用規則が未定義で、FR-01 の出題内容を検証できない

- 対象ファイル・箇所: `api-spec.yaml` `listSentences` description「以降のお題の切り替え(ローテーション・再利用含む)はフロントエンドがこの一覧をもとにローカルで行う」/ `screen-design.md` S-03
- 指摘内容: 順次か、シャッフルか、シャッフル後に使い切ったら再シャッフルかが未定義。FR-01 の受け入れ条件「お題が枯渇しない」だけならテストは書ける(例: 10文のセットで20文モードを開始し、20文出題されること)が、「N 文モードで N がセット件数を超えたとき同じ文が連続しないか」「順序が毎回同じか」といった検証はできない。乱数を使う実装ならテストのシード固定手段も必要になる。
- 推奨対応: 出題順の規則を screen-design.md S-03 か P3 `class-design.md` のどちらで確定するかを明記する。乱数を使う場合はテスト用にシードを注入可能にする旨を申し送る。

### B4. 「多い順」ソートの同値時タイブレークと表示件数が未定義

- 対象ファイル・箇所: `api-spec.yaml` `MissAnalysis.byKana` / `byErrorPattern` / `byPrevKana` / `screen-design.md` S-06
- 指摘内容: FR-10 の各観点は「多い順」とだけ定義され、**同数のときの二次ソートキー**が決まっていない。ミス回数が同じかなが複数あるテストデータでは、返却順が実装依存になり期待値を固定できない。加えて、配列を全件返すのか上位 N 件に絞るのか(requirements.md FR-10 受け入れ条件は「上位を確認できる」)も未定義で、「byKana に何件返るか」を検証できない。`GET /api/topic-sets` の「sort_order 順」も同様で、TBL-02 `sort_order` に UNIQUE 制約がないため重複値を投入したテストデータでは順序が不定になる。
- 推奨対応: 各ソートに二次キー(例: 同数ならかなのコードポイント昇順、`sort_order` 同値なら `id` 昇順)を定義し、返却件数の上限(全件 or 上位 N)を明記する。

### B5. 数値の丸め規則が未定義で、算出結果の期待値が桁レベルで一意にならない

- 対象ファイル・箇所: `table-definition.md` TBL-04 `net_kpm NUMERIC(6,2)` / `accuracy NUMERIC(5,2)` / `consistency NUMERIC(8,2)`、`api-spec.yaml` `SessionResult` / `MissAnalysis` の `number` 型フィールド
- 指摘内容: 保存桁数は決まっているが、丸め方(四捨五入・切り捨て・銀行家丸め)と、丸めをアプリ側で行うか DB の暗黙変換に任せるかが未定義。例えば correctKeyCount=2, 総キー3 の正確率は 66.67 とも 66.66 とも書ける。API レスポンスの `missRate` / `accuracyRate` は DB 型の裏付けがないため小数桁数すら決まっていない。FR-06/FR-10 のテストケースを書く際、期待値を「66.67」と固定できない。
- 推奨対応: 「小数第2位で四捨五入」等の丸め規則を1箇所(FR-06 は P3 の数式確定時、FR-10 は api-spec.yaml)で定義する。あわせて `net_kpm NUMERIC(6,2)` の上限(9999.99)を超える入力を受けたときの挙動も決める。

### B6. テスト実行時のシードデータが定義されておらず、前提データを固定できない

- 対象ファイル・箇所: `table-definition.md` TBL-03「シードデータとして開発者が投入する」
- 指摘内容: シード投入する旨は書かれているが、**何セット・何文投入するか**が定義されていない。FR-13 のテストケース「難易度一覧に3件表示される」、FR-01 の「初級セットを選ぶと初級のお題のみ出題される」といったケースで、期待値(件数・名称)をテスト設計者が独自に決めることになり、実装のシードとずれる。TBL-02 は `name` にも UNIQUE がないため、同名の難易度が複数投入されうる状態も許容される。
- 推奨対応: P2 か P3 のいずれかで、テスト・開発共通の最小シードセット(難易度名とその件数、各セットのお題件数の下限)を確定する文書を決めておく。

### B7. `users.name` の UNIQUE 制約とテストの独立性

- 対象ファイル・箇所: `table-definition.md` TBL-01 `name VARCHAR(100) NOT NULL, UNIQUE` / `api-spec.yaml` `identifyUser`(find-or-create)
- 指摘内容: 仕様(FR-12: 同名なら同一人物)としては正しいが、テスト実行の観点では次の問題がある。(a) 複数のテストケースが同じ名前を使うとデータが共有され、履歴件数や自己ベストが前のケースの影響を受ける(テスト間の独立性が崩れる)。(b) find-or-create を同一名で同時実行した場合の一意制約違反の扱い(500 か、リトライして 200 か)が未定義で、期待値が書けない。
- 推奨対応: (b) の同時実行時の挙動を api-spec.yaml に一文で定義する。(a) はテスト設計時に「ケースごとに一意な名前を生成する」方針を P4 test-plan.md に申し送る前提で、ここでは申し送りとして残せば足りる。

### B8. TBL-06 `char_type` に CHECK 制約がなく、TBL-05 と非対称

- 対象ファイル・箇所: `table-definition.md` TBL-06 `char_type VARCHAR(10) NOT NULL`(制約なし)vs TBL-05 `char_type ... CHECK IN ('清音','拗音','撥音ん','促音っ','長音')`
- 指摘内容: FR-10(4) の文字種別正解率は TBL-05 と TBL-06 の `char_type` を突き合わせて算出するのに、片側だけ値が制約されていない。TBL-06 に想定外の値が入っても DB は受理するため、「不正な char_type を含むリクエストを送ったときの期待値」が書けず、また集計が静かに壊れるケースを検出するテストも設計できない。あわせて、TBL-06 の UNIQUE 制約が `(session_id, kana)` である前提として「1つのかな文字列は1つの char_type にしか対応しない」ことが暗黙になっているが、その前提は明記されていない。
- 推奨対応: TBL-06 `char_type` にも同じ CHECK 制約を付ける。かなと char_type が 1:1 である前提を er-diagram.md 3.2 に明記する。

### B9. 「直近のミス位置」の表示解除条件が未定義

- 対象ファイル・箇所: `screen-design.md` S-03「確定済み文字・次に打つべき文字・直近のミス位置(リアルタイム更新)」
- 指摘内容: ミス位置がいつ消えるか(正しいキーを打った時点か、その拍を打ち終えた時点か、次のお題に移るまで残るか)が定義されていない。FR-03 のテストケース「誤入力後に正しいキーを入力するとミス表示がどうなるか」の期待値が書けない。screen-design.md 5章はビジュアルデザインを対象外としているが、これは見た目ではなく状態遷移の仕様であるため対象外にはならない。
- 推奨対応: S-03 の備考に、ミス表示の解除タイミングを一文で定義する。

### B10. 判定対象とするキー入力の範囲が未定義

- 対象ファイル・箇所: `screen-design.md` S-03「ローマ字キー入力(IME を介さない直接判定)」/ `api-spec.yaml` `MissRecordInput.actualKey`
- 指摘内容: 英字以外のキー(数字・記号・Shift/Ctrl 等の修飾キー・Backspace・矢印キー・Enter)を押したときに、ミスとして記録するのか無視するのかが定義されていない。また IME がオンの状態で入力された場合の挙動も未定義。FR-02/FR-04 の「不正入力」系テストケース(例: Backspace を押したときミスが1件増えるか)が書けない。
- 推奨対応: P3 `logic-spec/romaji-automaton.md` で「受理対象キー集合」と「無視するキー集合」を定義する旨を、screen-design.md S-03 または system-architecture.md 2章に申し送りとして記載する(P3 で決まると明記されていれば P4 で解決済みとして扱える)。

### B11. FR-08 履歴一覧の件数上限・ページングが未定義

- 対象ファイル・箇所: `api-spec.yaml` `listSessionHistory`(パラメータなし、配列を返す)
- 指摘内容: 全件返す仕様なのか件数上限があるのかが書かれていない。「セッション結果を 500 件投入したとき何件返るか」の期待値が決まらず、NFR-02(2秒以内)の負荷条件も定めようがない。また `played_at` は `DEFAULT now()` のため、テストで連続投入すると同一タイムスタンプになりうるが、その場合の降順ソートのタイブレークが未定義で並び順の期待値が固定できない。
- 推奨対応: 全件返す旨を明記するか件数上限を定義し、`played_at` 同値時のタイブレーク(`id` 降順など)を追記する。

## 重要度C(参考)

### C1. `listSentences` の 404 に対する画面側の挙動が明示されていない

- 対象ファイル・箇所: `api-spec.yaml` `listSentences` 404「指定したお題セットが存在しない、またはお題が0件」/ `screen-design.md` S-02 備考「お題セット取得失敗時は汎用エラー表示に切り替える」
- 指摘内容: S-02 の備考は `GET /api/topic-sets` の失敗を指しているようにも読め、「お題が0件のセットを選んで開始した場合」に S-02 に留まるのか S-03 に遷移してからエラーになるのかが読み取れない。テストは書けるが、遷移先の期待値がレビュー時に議論になりうる。
- 推奨対応: S-02 の備考を「お題セット一覧取得・お題文取得のいずれかが失敗した場合」に広げ、留まる画面を明記する。

### C2. localStorage の保存キー・異常時の挙動が未定義

- 対象ファイル・箇所: `screen-design.md` 2章「`userId` と名前は、ブラウザの localStorage に保存する」
- 指摘内容: 保存キー名・保存形式(JSON か個別キーか)が未定義なため、テストで localStorage を直接操作して初期状態を作る手順が書けない。localStorage が無効化されたブラウザや、壊れた値が入っていた場合(存在しない `userId` が残っている等)の挙動も未定義。P3 `class-design.md` でストア構造を決める旨は書かれているので、そこに含める前提であれば問題ない。
- 推奨対応: P3 でキー名と不正値検出時のフォールバック(S-01 に戻す)を決める旨を申し送る。

### C3. FK の削除時挙動が未指定で、テストデータのクリーンアップ順序が暗黙になる

- 対象ファイル・箇所: `table-definition.md` TBL-04/TBL-05/TBL-06 の FK 定義(`ON DELETE` 指定なし)
- 指摘内容: `ON DELETE` 未指定は PostgreSQL では `NO ACTION` になるため、テスト後のデータ削除は子テーブルから順に行う必要がある。設計書に書かれていないだけで実害はないが、P4 でテストデータのセットアップ/ティアダウン手順を書く際の前提になる。
- 推奨対応: P3 `db-access.md` で `ON DELETE` 方針を明記する際に、テストのティアダウン順序も申し送る。

### C4. `kana VARCHAR(4)` の桁数根拠

- 対象ファイル・箇所: `table-definition.md` TBL-05/TBL-06 `kana VARCHAR(4)`
- 指摘内容: 拗音「しゃ」(2文字)は収まるが、上限4文字がどの拍を想定した値なのかが書かれていない。P4 で「最長のかな1拍」を含むテストデータを作る際、境界値をどこに置くかの判断材料がない。
- 推奨対応: P3 の受理表確定時に「かな1拍の最大文字数」を確認し、桁数の根拠を一言添える。

### C5. NFR-09 の DB 接続断をテストで再現する手段が未定義

- 対象ファイル・箇所: `nonfunctional-design.md` NFR-09
- 指摘内容: 「500 を返す」「フロントエンドは汎用エラー表示」という期待値は明確でテストケースは書ける。ただし、結合テストで DB 接続断をどう再現するか(コンテナ停止・接続プールの意図的な枯渇・モック)が書かれていないため、テスト手順の設計は P4 側の裁量になる。
- 推奨対応: P4 `test-plan.md` に再現手段を決める項目として申し送る(設計書の修正は不要)。

## 観点別の総括

**1. 入出力の一意性** — 問題あり。データ構造(スキーマ・カラム・型)のレベルでは非常によく定義されており、`SessionSubmission` → `SessionResult` の項目対応や、FR-10 の各集計の分母・分子(`api-spec.yaml` の description に式が書かれている)は明快で、この点は P2 成果物として水準が高い。一方で「複数正解がある入力に対して何を記録するか」(A1)、「boolean 1個で表現された複合条件」(A3)、「丸め」(B5)、「ソートのタイブレーク」(B4)といった、**値が一意に決まらないポイント**が残っている。

**2. 異常系・エッジケースの網羅** — 空データ(0件)系は `screen-design.md` 4章と各 API の description で網羅的に定義されており、「0件」と「値が0」を区別している点は特に良い。P4 でそのまま空状態のテストケースに落とせる。他方、**不正入力系(4xx)が完全に空白**(A2)であり、ここが最大の欠落。DB 接続断は 500 一様返却として一貫して定義されており、テストは書ける(C5 は手順の話)。

**3. 非機能要件の測定可能性** — 数値目標を持つのは NFR-01(50ms)と NFR-02(2秒)の2つのみで、いずれも計測ツールへの言及はあるが計測区間・合否基準がない(B1/B2)。NFR-03〜NFR-08 は数値目標を持たず方式のみの定義であり、「HTTPS で接続できる」「環境変数から DB 接続情報を読む」「起動ログが出る」といった確認ベースのテストで足りるため、テスト可能性の観点では問題なし。

**4. テストデータの再現性** — 制約設計そのものは妥当で、`(session_id, kana)` の UNIQUE や CHECK 制約がテストデータ生成の致命的な妨げになる箇所は見当たらなかった。ただしシードデータの内容が未確定(B6)、`users.name` UNIQUE によるテスト間干渉(B7)、TBL-06 の CHECK 欠落(B8)、`played_at`/`sort_order` の同値時順序(B4/B11)が、再現性を下げる要因として残る。

**5. P4 完了条件の見通し** — 13 の FR のうち、FR-07・FR-08・FR-12・FR-13 は現状のままでもテストケースを列挙できる。FR-01・FR-09・FR-10 は A1/A3/B3/B4 の解消が前提。FR-04 は A1、FR-05・FR-06 は A2 の解消が前提。FR-02・FR-03・FR-11 は P3(受理表・算出式・アドバイス生成)の成果物が出てからテストケース化する前提であり、これは工程順として正常。**A1〜A3 の3件を閉じれば、P4 の「全 FR-ID にテストケース ID が1件以上紐づく」状態には到達できる見通し**と判断する。
