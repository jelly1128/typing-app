## 重要度A(必須)

### A1. 「拍」の定義が、requirements.md/use-cases.md で確定した粒度の使い分けと矛盾している

- 対象ファイル・箇所: `glossary.md` 1章「拍(はく)/ かな1拍」の定義文、および 2章「キー入力(判定単位)」の定義文
- 指摘内容:
  glossary.md 1章は「拍(はく)/ かな1拍」を **「日本語における発音・入力判定の最小単位」** と定義している。つまり「拍」が入力判定の最小単位であると読める。
  しかし requirements.md 0章・use-cases.md 0章は(P1中間レビュー指摘A1対応として)「判定単位はローマ字1キー」「分析単位はかな1拍」と明確に使い分けを確定しており、FR-02/FR-03 の入力判定はキー単位、FR-04/FR-10 のミス分析が拍単位である。
  さらに glossary.md 自身も 2章「キー入力(判定単位)」の項で「FR-02/FR-03 における正誤判定の最小単位。ローマ字のアルファベット1文字ずつを指す(**拍単位ではない**)」と明記しており、同一文書内で 1章と 2章の記述が直接矛盾している。
  用語集は「同じ概念に異なる言葉・粒度を使っていないか」を実装者が最初に確認する文書であるにもかかわらず、その用語集自体が確定済みの粒度区分を誤って記述しているため、読者(将来の自分を含む)が「拍単位で入力判定してよい」と誤読するリスクが高い。
- 推奨対応:
  1章「拍」の定義文から「・入力判定」を削除し、「日本語における発音の最小単位」に修正する。加えて「ミス分析(FR-04/FR-10)の集計単位でもある」旨を明記し、2章の「キー入力(判定単位)」の記述(判定単位はキー、拍単位ではない)と整合させる。可能であれば、requirements.md/use-cases.md の 0章で使っている「判定単位=ローマ字1キー、分析単位=かな1拍」の文言をそのまま引用し、粒度の使い分けを glossary.md 側でも一段落として明示するとよい。

## 重要度B(推奨)

### B1. 「受理候補」が定義されていない

- 対象ファイル・箇所: `use-cases.md` UC-02 基本フロー1「ローマ字読みの受理候補を表示する」/ `glossary.md` 2章
- 指摘内容: glossary.md は「ローマ字入力判定まわりの用語」を定義する文書であると冒頭で宣言している。UC-02 の中核的な語である「受理候補」(FR-02 の複数表記許容の結果、システムが正解として受け付けるローマ字パターン群を指すと推測される)が、glossary.md のどの項目にも定義されていない。「ローマ字表記ゆれ」の項目で概念自体は間接的に触れられているが、「受理候補」という語そのものへの言及はない。
- 推奨対応: 2章「ローマ字入力」に「受理候補」の項目を追加し、「表記ゆれを含め、あるキー入力の時点でシステムが正解として受理しうるローマ字パターンの集合」といった定義を加える。P1の叩き台としては必須ではないが、P3 のオートマトン設計で頻出する語になるため、早めに glossary.md に固定しておくと以後の設計文書の記述がぶれにくい。

## 重要度C(参考)

### C1. 撥音「ん」の定義が FR-02 の例外条件を省略している

- 対象ファイル・箇所: `glossary.md` 1章「撥音「ん」」の定義文
- 指摘内容: glossary.md は「"n" 単独または "nn" のいずれかで表記される」とだけ記述しており、FR-02 が明記する「次の入力文字によっては "n" 単独では確定できない(母音や"y"が続く場合は"nn"が必要)」という条件が省略されている。「(FR-02 参照)」と付記されているため実害は小さいが、glossary.md 単体を読むと「常にどちらでもよい」と誤読されうる。
- 推奨対応: 定義文末尾に「ただし常に両方が使えるわけではない(詳細はFR-02参照)」の一言を足す。P3 のオートマトン設計時に確定させれば足りるため、P1 のブロッカーにはしない。

### C2. 「ヘボン式」「訓令式」は requirements.md / use-cases.md 側で未使用の語

- 対象ファイル・箇所: `glossary.md` 2章「ヘボン式」「訓令式」
- 指摘内容: glossary.md 冒頭は「use-cases.md / requirements.md で使う…用語を定義する」と範囲を宣言しているが、「ヘボン式」「訓令式」という語自体は requirements.md にも use-cases.md にも登場しない(FR-02 は方式名を出さずローマ字表記の実例だけを列挙している)。「ローマ字表記ゆれ」が生まれる背景説明としては有用だが、文書の宣言した収録範囲(2文書で使う語)からは厳密には外れている。
- 推奨対応: 実害はないため修正必須ではない。気になる場合は「(背景知識・補足)」等の注記を添えるか、そのままでよい。

## 観点別の総括

- **トレーサビリティ**: glossary.md は FR-02/FR-03/FR-04/FR-10 への参照を各所に付けており、参照先はいずれも requirements.md 上に実在する。参照そのものの欠落・誤参照は見つからなかった。ただし A1 の通り、参照先(requirements.md 0章)の内容と矛盾する記述が残っている。
- **charter.md との整合性**: 「し=si/shi/ci、ん=n/nn、っ=子音重ね」等、charter.md 3.1 の MVP スコープ記載と glossary.md の表記ゆれ関連定義は一致している。3.2 のスコープ外リストと矛盾する記述もない。問題なし。
- **内部矛盾・曖昧さ**: A1 が主要な矛盾。それ以外の用語(清音・拗音・促音・長音・KPM系・お題・セッション等)は requirements.md / use-cases.md の記述と定義・粒度・具体例が一致しており、他に一意に解釈できない箇所は見当たらなかった。
- **完了条件の充足**: glossary.md は workflow.md P1 の完了条件(MVP全機能へのFR-ID付与・スコープ外明記)に直接紐づく文書ではないため、この観点は依頼どおり評価対象外とした。
- **過剰・スコープ超過**: C2 以外に、機能スコープを広げるような記述は見当たらなかった。C2 も文書の記述範囲の話であり、charter.md 6章の「完走優先」方針に反するような実装コスト増加要因ではない。
