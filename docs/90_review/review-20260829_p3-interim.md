### A2. 「ん」の "nn" が原理的に受理不能。FR-02 受け入れ条件3・charter 3.1 #1 を満たしていない

- 対象ファイル・箇所: `romaji-automaton.md` 6章(判定オートマトン、`もし 候補集合の中に 入力済み文字列 と完全一致するパターンが存在する: この拍を確定する`)、5.1
- 指摘内容:
  - 6章のオートマトンは「入力済み文字列が候補と**完全一致した瞬間に確定**」する。候補集合に `{"n", "nn"}` のように**一方が他方の真の接頭辞**である組が含まれる場合、短い方が必ず先に確定し、長い方(`"nn"`)には到達できない。
  - 具体例(お題「こんばんは」): こ=`ko` → ん(次拍=ば、子音行)候補`{n, nn}` → キー `n` で `"n"` が完全一致 → **即確定** → 次拍「ば」の候補は `{ba}` → 続くキー `n` は候補集合が空になり **ミス記録**。つまり実際のIMEで最も一般的な打ち方 `konnbannha` が全編ミス判定になる。
  - これは `requirements.md` FR-02 受け入れ条件3「単独の "n" と "nn" の**両方**を許容する」、`charter.md` 3.1 #1「ん=n/nn」に対する明確な未達。5.1 の関数は正しく `{"n","nn"}` を返しているのに、6章の確定規則がそれを潰している。
  - 併せて、6章には**先読み(1キー保留)と押し戻し**の概念が一切ない。最長一致を許すと必ず「保留中に来たキーを現在の拍が食うのか、次の拍へ回すのか」という規則が要る(例: ん保留中に `k` が来たら ん=`n` 確定+`k` は次拍へ押し戻し、`n` が来たら ん=`nn` として消費)。この規則が無いままでは実装者が一意に書けない(P3 完了条件「設計書だけで実装を書き切れる粒度」に未達)。
  - さらに、保留中に来たキーが「延長候補にも次拍の先頭にも一致しない」場合、ミスをどちらの拍に記録するか(FR-04 の `対象拍`)も未定義。
- 推奨対応: 6章に確定規則を明文化する。最低限、(a) 完全一致しても、その文字列を真に延長する候補が残る場合は確定を保留する、(b) 次のキーが延長候補と一致すれば延長、一致しなければ短い方で確定し**そのキーを次拍へ押し戻す**、(c) 押し戻したキーが次拍の候補にも一致しない場合のミス帰属先、の3点を疑似コードに反映する。9章のテストベクタ申し送りにも「`n`/`nn` 両方で受理されること」「押し戻しケース」を追加する。

### A3. 促音の「次拍候補の絞り込み」が判定関数に反映されない(関数シグネチャ不整合・戻り値の行き先なし)

- 対象ファイル・箇所: `romaji-automaton.md` 5.2 の `関数 次の拍の受理パターンを絞り込む(次の拍候補群, っで確定したパターン)` と 6章の呼び出し `次の拍の候補群を絞り込む(次の拍, っで確定したパターン = 入力済み文字列)`
- 指摘内容:
  - 関数名が一致していない(「次の拍の受理パターンを絞り込む」 vs 「次の拍の候補群を絞り込む」)。第1引数も「候補群」と「拍」で型が違う。
  - より重大な点として、この関数の**戻り値がどこにも代入されていない**。次拍の処理は `拍を判定する(拍, 次の拍)` が呼ばれ、その中で `受理パターン集合` を**4章の表から引き直す**ため、絞り込み結果は捨てられる。`拍を判定する` に絞り込み済み候補を受け取る引数が無い。
  - 結果として、5.2 の根拠(「っで `s` を確定した場合、次拍『し』は si/shi のみ許容(ci は不許可)」)が実装に落ちない。「っし」で `s` → `ci` と打つ列(`sci`)が正解扱いになる。9章のテストベクタ申し送り(「っし → s/c の一貫性」)も現状の疑似コードでは失敗する。
- 推奨対応: `拍を判定する(拍, 次の拍, 事前絞り込み候補=なし)` のように引数を追加し、6章の促音確定時に絞り込み結果を次の呼び出しへ引き渡す形に書き直す。関数名・引数名も5.2と6章で統一する。

### A4. `byCharType` の出現0件文字種が未定義。0除算と誤アドバイスを生む(3文書で規定が食い違う)

- 対象ファイル・箇所: `advice-generation.md` 1章(`byCharType // [{charType, accuracyRate}] 5種類全件`)、2章 カテゴリ3 / `api-spec.yaml` `MissAnalysis.byCharType` / `screen-design.md` 4章 B2
- 指摘内容:
  - `api-spec.yaml` の定義式は `accuracyRate = (該当文字種の出現回数合計 − 拍単位ミス数) ÷ 該当文字種の出現回数合計`。**出現回数合計が0(その文字種が一度も出題されていない)の場合は0除算**で、api-spec にはこのケースの規定がない。初級お題に促音「っ」や長音「ー」が含まれないことは普通に起こる。
  - `advice-generation.md` は入力契約として「**5種類全件**」返ることを前提に、カテゴリ3で `accuracyRate` 最小値を無条件に選ぶ。出現0の文字種が 0(または未定義)で返ってくると「促音っの正解率が0%とやや低めです。促音っを含むお題を選んで練習すると効果的です」という、**一度も出題されていない文字種に対する誤ったアドバイス**が生成される。
  - `screen-design.md` 4章 B2 は「ミスがないため全文字種100%」と書いており、「5種類全件」という前提は screen-design 由来だが、これは “ミス0件” のケースの記述であって “出現0件” のケースを規定していない。3文書のいずれにも出現0件時の規定がない。
  - 加えて、カテゴリ3には**最低出現回数の閾値がない**。カテゴリ2は「総出現回数(推定) >= 5」を課しているのに、カテゴリ3は1回出題して1回ミスすれば正解率0%で即該当する。同一文書内で判定の粒度が不揃い。
  - `byCharType` が空配列で返る可能性(セッション0件は先に弾かれるが、それ以外の経路)に対する疑似コードのガードもない。
- 推奨対応:
  1. `api-spec.yaml` `byCharType` に「出現回数合計が0の文字種は配列に含めない(または `accuracyRate: null`)」を明記し、`screen-design.md` S-06 の表示規則も合わせる(→ CL-006/007 として `change-log.md` に記録)。
  2. `advice-generation.md` 1章の入力契約を上記に合わせて修正し、カテゴリ3に最低出現回数の閾値と `byCharType` 空時のガードを追加する。
  3. 最小値が複数ある場合のタイブレーク規則も1行決める(テストベクタの期待値が一意に決まらないため)。

### A6. 総キー入力数=0 のとき `accuracy = 100` を返す既定値が FR-09 自己ベストを恒久的に汚染する(設計判断メモ#3の根拠が制限時間モードで成立しない)

- 対象ファイル・箇所: `session-metrics.md` 2.4、4章 判断#3 / `api-spec.yaml` `SessionResult.isAccuracyBest` / `requirements.md` FR-09
- 指摘内容:
  - 4章 判断#3 は「FR-05 によりセッションは終了条件を満たした場合のみ保存されるため実運用では発生しにくい」を根拠にしているが、**制限時間モードでは1キーも打たずに終了条件(時間経過)が成立する**。`api-spec.yaml` の400条件にも `correctKeyCount=0` を弾く規定はない(`durationSeconds` が1未満のみ)。つまり「1打鍵もしていないセッションが正確率100%で保存される」経路が正規に存在する。
  - `api-spec.yaml` `isAccuracyBest` は「厳密に上回った場合 true(同値は false)」のため、一度 100% が自己ベストとして記録されると、その難易度の正確率ベストは**二度と更新できない**。FR-09(自己ベスト表示)の値が意味を失う。
  - 同様に `consistency = 0` も「データ不足」と「完全に安定(最良)」が同じ値になる(B7 参照)。既定値を “最良側” に倒している点が共通の問題。
- 推奨対応: いずれかを選び、`session-metrics.md` 4章の根拠も書き換える。(a) `api-spec.yaml` に「`correctKeyCount + missRecords.length == 0` は400」を追加して保存させない、(b) 総キー入力数=0 のとき `accuracy = 0` とする、(c) 自己ベスト集計から総打鍵0のセッションを除外する。(a)(c) は `api-spec.yaml` の変更を伴うため `change-log.md` への記録が必要。

## 重要度B(推奨)

### B1. `byKana[0]` のみを見る判定は、`byKana` のソートキーが未定義なため一意に解釈できない

- 対象ファイル・箇所: `advice-generation.md` 2章 カテゴリ2 / `api-spec.yaml` `byKana`(「かな1拍別のミス回数・ミス率(**多い順**)」)
- 指摘内容: 「多い順」が `missCount` 順か `missRate` 順か api-spec で確定していない。カテゴリ2の閾値は `missRate >= 30` を含むため、`missCount` 降順ソートだと「回数は2位だがミス率50%のかな」が永久に拾われない。先頭1件しか評価しない設計とソート順の未定義が組み合わさって、出力が実装依存になる。
- 推奨対応: api-spec に「`missCount` 降順、同数なら `missRate` 降順」等を明記した上で、カテゴリ2は「閾値を満たす先頭1件」を上位N件から探索する形に直す(1カテゴリ1件という上限は維持できる)。

### B2. `総出現回数(推定) = missCount ÷ (missRate ÷ 100)` は逆算依存で脆く、0除算のガードがない

- 対象ファイル・箇所: `advice-generation.md` 2章 カテゴリ2
- 指摘内容: `missRate` の丸め規則が `api-spec.yaml` に無いため、実装が小数0桁で丸めると低ミス率のかなで `missRate = 0` になり **0除算**。丸めがある限り推定出現回数の誤差も大きい(missRate=33 と 33.3 で推定値が変わる)。分母の実データ(`session_kana_counts.total_count`)は API 側に存在するのに逆算しているのが根本原因。
- 推奨対応: `api-spec.yaml` の `byKana` に `totalCount`(そのかなの総出現回数)を追加するのが本筋(P4 のテスト設計前なら影響は小さい)。追加しない場合でも `missRate > 0` のガードを疑似コードに明記する。

### B4. advice 配列の「表示順」が `api-spec.yaml` / `screen-design.md` に書かれていない

### B5. `expected_key` の記録規則が「解決」ではなく再先送りになっている

- 対象ファイル・箇所: `romaji-automaton.md` 7章 / `table-definition.md` 未決事項(121行目) / `api-spec.yaml` `MissRecordInput.expectedKey`
- 指摘内容: `table-definition.md` は「P3 `logic-spec/romaji-automaton.md` の**受理表確定と合わせて定める**」と約束していたが、7章は `db-access.md`(P3-06)へ再度先送りしている。P3 内での移送なのでゲート③までに閉じれば運用上は許容範囲だが、先送り先が変わった事実が上流に反映されていない。また判断材料は既に揃っている: 6章の `期待キー候補` は**集合**で返る一方、TBL-05 `expected_key` は単一 `VARCHAR(10) NOT NULL`、かつ FR-10(2) の誤りパターン集計は `(expectedKey, actualKey)` でグルーピングするため、集合を連結して保存すると集計が断片化する。
- 推奨対応: `table-definition.md` の未決事項に「確定先を `db-access.md` に移す(2026-08-29)」と追記。`db-access.md` では「代表1キーを保存する場合の代表の選び方(例: 表の先頭表記/画面ヒントに出していた表記)」と FR-10(2) の集計影響をセットで決める。`VARCHAR(10)` の妥当性(受理表確定後は期待キーが常に1文字なので十分)もその場で結論を書く。

### B6. `子音種別` の定義が名称と実体でずれ、「ん + な行」の扱いが記述されていない

- 対象ファイル・箇所: `romaji-automaton.md` 3章(`子音種別: 母音行(あ/や行) | 子音行(それ以外)`)、5.1
- 指摘内容: 「子音種別」という属性名なのに値が「母音行/子音行」で、`glossary.md` にも無い独自語。5.1 の根拠文は「"n" 単体は次にくる**母音・"y"** と結合して別の拍に読めてしまう」としているが、実際には **な行**が続く場合も打鍵列の解釈に影響する(`konni` と `konnni` の差)。3章の分類だけでは実装者が「な行は子音行だから `{n, nn}` 両方許容」と読むが、A2 の保留規則を入れた瞬間に な行の扱いが独立の分岐になる。
- 推奨対応: 属性名を「次拍先頭種別」等に改め、値を「母音始まり / や行 / な行 / その他子音」の4分類にし、5.1 と A2 の保留規則の両方で参照する。`glossary.md` に用語追加は不要(仕様書内の局所語である旨を明記すれば足りる)。

### B7. `consistency = 0` が「データ不足」と「完全に安定」の二義になる

- 対象ファイル・箇所: `session-metrics.md` 2.5
- 指摘内容: 打鍵間隔が1件以下のとき 0 を返すが、0 は「ばらつきゼロ=最良」とも読める値。S-04/S-05 に表示される数値なので利用者にも誤解を与える。A6 と同根(既定値を最良側に倒している)。
- 推奨対応: 「間隔が2件未満の場合は算出不能として画面に『—』を表示する」等の扱いを決め、`screen-design.md` の表示規則にも反映する。DB は NOT NULL のため 0 保存自体は維持してよいが、その旨を明記する。

### B8. `NUMERIC(8,2)` で足りる根拠が示されていない(お題N文モードは所要時間に上限がない)

- 対象ファイル・箇所: `session-metrics.md` 2.5 末尾「桁数が確保されており、変更不要と確認した」
- 指摘内容: 標準偏差[ms]の上限は打鍵間隔の最大値に依存する。`time_limit` モードは `api-spec.yaml` の400条件で600秒上限があるが、`sentence_count` モードには所要時間の上限がなく、長時間放置すれば間隔が 10^6 ms を超え `NUMERIC(8,2)`(最大 999999.99)を**オーバーフローさせて保存が失敗する**。「確認した」と書く以上、この上限計算を根拠として残すべき。
- 推奨対応: 上限の見積もりを1行書く。合わせて「上限を超える場合は上限値でクリップする」または桁数拡張のどちらかを決め、`table-definition.md` の未決事項消し込み(A5)と同時に反映する。

### B9. 丸めモードが未定義。共有テストベクタの同値性検証が成立しない

- 対象ファイル・箇所: `session-metrics.md` 3章(「小数第2位で丸め」)、`advice-generation.md` 3章(「整数に丸め」)
- 指摘内容: 四捨五入/偶数丸め/切り捨てのどれかが未定義。CLAUDE.md の目的(`shared/testdata` で他言語実装の同値性を保証)に照らすと、丸めモードが決まっていない限り期待値が一意にならない(P9 移植時に必ず差分が出る箇所)。平方根・除算の演算順序も同様。
- 推奨対応: 「小数第3位を四捨五入(half-up)」等を1行明記する。P4 のテストベクタ作成前に必要。

### B10. 受理表が扱うかなの集合(お題データ側の制約)が定義されていない

- 対象ファイル・箇所: `romaji-automaton.md` 3章の前提、4章
- 指摘内容: 4章の表は現代標準のかなのみ。`table-definition.md` TBL-03 `reading VARCHAR(200)` に何を入れてよいかの制約が無いため、シードデータ作成者(=実装者)が判断できない。未定義なのは少なくとも: 句読点「、」「。」・空白、外来音(ファ/ティ/ヴァ等)、小書き単独(ぁぃぅぇぉ)、「を」の `o` 表記可否、カタカナ表記の可否。読みに「、」が含まれた瞬間、6章のオートマトンは受理パターンを引けずミス扱いになる。
- 推奨対応: 3章の前提に「`reading` に使用してよい文字集合」を列挙し(4章の表の見出し語+「ー」+「ん」「っ」に限定するのが最小)、範囲外はシードデータ投入時に排除する旨を書く。5.2 の促音の前提(子音行の直前のみ)と同じ扱いで並べるとよい。

### B11. `pattern` テンプレートの「直近の集計で」という文言が1章の前提と矛盾する

- 対象ファイル・箇所: `advice-generation.md` 3章 `pattern` テンプレート / 同 1章(「全期間・全難易度の累積データである点に注意」)
- 指摘内容: 集計対象は全期間累積なのに、利用者に見える文面は「直近の集計で{count}回」。利用者が期間を誤解する。
- 推奨対応: 「これまでの練習で{count}回」等に変更する。

## 観点別の総括

**1. FR-ID トレーサビリティ**
3文書とも冒頭に対応 FR を明記しており、書式は守られている。ただし内容面で FR-02 受け入れ条件3(ん=n/nn、A2)と条件5(長音、A1)を満たしておらず、FR-11 の閾値/文言は網羅されているが FR-09 に副作用がある(A6)。上流の未決事項消し込みが3箇所漏れている(A5)。`romaji-automaton.md` が FR-03/FR-04 の対応表(6章末尾・7章)を持っている点は良い。

**2. 前工程との整合性(重点: advice 配列)**
重点確認対象については、**件数(0〜3件)・「セッション0件なら空配列」・「該当なしなら good 1件」・「good と具体的指摘は混在しない」の4点が `advice-generation.md` / `api-spec.yaml`(194〜199行・486〜493行)/ `screen-design.md`(103行・115行)の3文書で一致していることを確認した**。矛盾はない。記述漏れは配列の順序保証のみ(B4)。`change-log.md` CL-005 の記録内容も実際の変更(advice を配列化、エンドポイント説明、S-06 表示項目、4章 B2)と一致しており、原因記述も具体的で運用ルールを満たしている。一方、CL-005 以外の上流変更(長音仕様 A1、byCharType 出現0件 A4)は change-log に載っていない。

**3. 言語非依存性**
疑似コード本体は3文書とも言語構文に依存しておらず、データ型・制御構造の書き方も移植可能。`romaji-automaton.md` 冒頭の注記だけが言語名を含む(B3)。API フィールド名(camelCase)の使用は言語ではなく IF 定義由来なので問題なし。丸めモード未定義(B9)は「言語非依存に書けているか」ではなく「言語をまたいで同じ結果になるか」の観点で要対応。

**4. ロジックの論理的な穴**
最も指摘が集中した観点。A2(最長一致・先読み欠落)、A3(絞り込み結果が伝播しない)、A4(0除算・出現0件)、A6(既定値の副作用)、B2(0除算)。`session-metrics.md` は0除算を明示的に扱っており設計態度としては良いが、既定値の選び方(最良側に倒す)に問題が残る。`romaji-automaton.md` 6.1 の具体例トレースは可読性に大きく貢献しているが、例に選んだ「し」「っこ」がどちらも接頭辞衝突のないケースで、A2 の欠陥を露呈させない例になっている点は示唆的。

**5. 設計判断の妥当性**
`romaji-automaton.md` 8章(5件)、`session-metrics.md` 4章(3件)、`advice-generation.md` 4章(3件)いずれも却下案と理由が対で記載され、書式は良い。内容は概ね筋が通っている(母標準偏差の採用理由、Consistency が FR-09 の比較対象でないこと、閾値を暫定値と明示して P6/P8 で見直す方針は charter.md 6章の完走優先方針と整合)。妥当でないのは `session-metrics.md` 判断#3 の前提(制限時間モードを見落とし、A6)と、`romaji-automaton.md` 判断#1 が上流要件の否定であるのに ADR 化・change-log 記録が未了である点(A1)。

**6. スコープ**
charter.md 3.2 のスコープ外項目(英語モード・かな入力等)への逸脱はない。促音の独立表記(xtu/ltu 等)の追加は FR-02 の「複数表記許容」の範囲内で、受理表に4パターン足すだけの増分であり過剰ではない。アドバイス複数化も MVP #8 の範囲内。P3 として過剰に踏み込んでいる箇所も見当たらない(むしろ `expected_key` など `db-access.md` へ回す判断は妥当)。

**7. ゲート③に向けて**
本票は中間レビューだが、A1〜A6 はいずれも「上位文書との矛盾」「実装が一意に書けない」に該当し、workflow.md のゲート通過条件(重要度A全件クローズ)の対象。特に A2・A3 は残り成果物(`class-design.md` / `sequence.md`)の記述に直接影響するため、**残りの P3 成果物に着手する前に romaji-automaton.md 6章を修正することを推奨**する。A1・A4・A5 は上流文書(requirements.md / glossary.md / api-spec.yaml / screen-design.md / table-definition.md)の修正と `change-log.md` への記録を伴うため、まとめて1セッションで処理するのが効率的。
