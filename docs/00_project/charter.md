# プロジェクト憲章

## 1. プロジェクトの目的

日本語タイピングアプリを開発する。ただし**アプリの完成は3つの目的のうちの1つ**に過ぎない。

| # | 目的 | 達成の判定 |
|---|---|---|
| 1 | SI 企業風のウォーターフォール工程を一通り体験する | 全工程の成果物が `docs/` に揃い、各ゲートのレビュー指摘 A が全件クローズしている |
| 2 | Claude Code の機能(commands / agents / skills / rules / hooks)を実地で整備する | `.claude/` に全種類が1つ以上動作する状態で存在する |
| 3 | build → deploy → document のフルループを一度通し切る | 公開 URL を他人に渡せ、README が書かれている |

## 2. プロジェクト全体の完了条件

> **公開 URL で他人がタイピングでき、記録が DB に残り、`docs/` に要件〜テストの全成果物が揃い、工程別の見積り/実績ズレ率が数値で出ている状態。**

## 3. スコープ

### 3.1 MVP(叩き台 — P1 で正式確定)

| # | 機能 |
|---|---|
| 1 | お題の日本語文を表示し、ローマ字入力を判定する(複数表記許容: し=si/shi/ci、ん=n/nn、っ=子音重ね) |
| 2 | セッション実行(お題 N 文 または 制限時間) |
| 3 | リアルタイム表示(確定文字 / 次に打つ文字 / ミス位置) |
| 4 | 結果算出(KPM、正確率、所要時間) |
| 5 | 結果を PostgreSQL に保存 |
| 6 | 履歴一覧 + 自己ベスト表示 |
| 7 | お題セット管理(DB 保持、難易度別) |

**ユーザー識別は「名前入力のみ」**とする。認証(Spring Security + JWT)は学習価値が高いが +2〜3 セッションかかるため MVP 外とし、完走を優先する。

### 3.2 スコープ外(拡張バックログ)

認証 / ランキング / 苦手キー分析 / お題投稿 / WebSocket 対戦 / 英語モード / かな入力

### 3.3 規模感

テーブル 4(`users` / `sentences` / `typing_sessions` / `session_results`)、API 6 本、画面 4(トップ / タイピング / 結果 / 履歴)

## 4. 技術スタック

| 層 | 選定 | 備考 |
|---|---|---|
| フロント | Vue 3 + Vite + TypeScript + Pinia | |
| バック | Java 25 + Spring Boot 4.x + Maven マルチモジュール | Spring Boot 4.0 が Java 25 を first-class support |
| DB | PostgreSQL 16 + Flyway | ローカルは Docker コンテナ |
| デプロイ | Render(Web Service + Managed Postgres) | Fly.io が次点。AWS は +3 セッションのため P9 送り |

### 4.1 モジュール構成の方針

`backend/typing-core/` を**言語非依存の純粋ロジック**として物理的に分離する(Maven マルチモジュール)。

- 単一モジュール + パッケージ分離より初期設定が +0.5 セッション重いが、依存の混入をビルドレベルで強制的に防げる
- 中核は**ローマ字入力受理オートマトン** — 外部依存ゼロの状態機械。テストしやすく、他言語への移植題材として理想的
- 仕様は `docs/30_detail-design/logic-spec/` に**言語名を出さない疑似コード**で書く
- 正しさは `shared/testdata/` の共有テストベクタ JSON で検証する。**他言語実装は同じ JSON を通すことで同値性を保証する**

## 5. 制約・前提

| 項目 | 内容 |
|---|---|
| 開発体制 | 1人(Kazuki)+ Claude Code |
| 稼働 | 1セッション 2〜3時間、休日中心 |
| 全体規模 | 22〜30 セッション ≒ 3〜4 ヶ月 |
| レビュー | レビュアーが居ないため、独立コンテキストのサブエージェントで代替する |
| コスト | Render 無料枠の範囲で収める |

## 6. リスクと対策

| リスク | 対策 |
|---|---|
| **デプロイまで到達せず未完で終わる** | P2.5 で Walking Skeleton を先に本番へ出す。デプロイを最後のご褒美にしない |
| 実装が膨らんで工程が終わらない | P5 が 8 セッションを超えたら履歴画面を切って P6 へ進む |
| 「情熱の先払い見積もり」で着手が遅れる | セッション冒頭の `/ty-plan` で必ず当日ゴールを1行に固定する |
| 設計とコードが乖離する | 差異を見つけたら**先に設計書を直す**。差異は `change-log.md` に記録する |
| 見積もり精度が上がらない | 毎セッション `estimate-actual.md` に見積/実績/要因を追記し、P8 で補正係数を算出する |
