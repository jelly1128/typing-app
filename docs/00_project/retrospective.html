分類とタスク性質

タスクの所要時間は「ボリューム」「複雑度」「新規設計判断の有無」ではなく、実装・作業中にKazukiとの質問・相談・報告の往復が発生するかどうかで最もよく説明できることが、P6〜P7を通じて実証された。この軸で全タスクを6分類する。

① 往復ゼロ — 補正係数 0.37倍

Claudeが選択肢・ドラフト・コードを単独で用意し、Kazukiが意思決定・確認のみ行うタスク。P1-07, P2-05, P2-06b, P2-07, P2.5-06, P3-01, P3-03, P5-02, P5-03, P5-11, P5-13, P5-18, P6-00a, P6-00b, P6-01, P6-02, P6-03, P6-04, P7-00a+00b, P7-01, P7-03(平均-63.5%)。

同じ「Claudeドラフト・Kazuki意思決定のみ」という枠でも、説明の往復が1回でも発生するかでさらに細分できる可能性があったが(P6-02〜04で「往復ゼロはさらに一段低い」という仮説が立った)、P7でも0.3〜0.4倍の範囲に収まり続けており、実務上はこの1分類で十分な精度が出ている。

② 統合・結合系 — 補正係数 0.29倍

P5-19、P7-06。「初めて結合するか」ではなく「結合対象が既に複数回のコードレビューで潰し込み済みか」が下振れの主因。レビュー未実施の初結合であれば、この係数は適用せず素直な見積もりに戻すべき。

③ 設計確定済み・機械的翻訳 — 補正不要

設計書(class-design.md / db-access.md / romaji-automaton.md 等)に未解決の判断が残っていないタスクは、複雑度に関わらずほぼ0%で着地する。P3-04〜08(再見積後)・P5-05〜10/12/14/16/17・REV-014 B1〜B3・P7-02/04/05/07 など約20件。「設計書に迷う余地が残っているか」を見積もり前に確認する運用が最も効果の高い補正であり、標準倍率の掛け算より優先して適用すべき。

④ 手戻り型 — 補正対象外(個別判断)

指摘対応で実際に複数ファイルを書き直すタスクは符号が割れる(P2-06a +172%、P3-09指摘対応 -37%、P6-07 +100%)。ズレの正体は「往復の有無」ではなく「作業内容が事前に確定しているか、実施結果次第で分量が変わるか」という別軸。対策は倍率補正ではなく分離見積もり(文書更新は定量、レビュー対応は発見都度・合意値なしで実績のみ記録)。P7-07で実際に機能し、P6-07のような超過が再発しなかった。

総合補正係数

工程を横断して単一の「自分の見積もりは平均N倍」を出すなら、①・②が大半を占め③がほぼ0%(=見積もりどおり)であることを踏まえ、

タスク性質を分類できた場合は分類別の係数(0.37倍 / 0.29倍 / 1.0倍)を使う。分類が付けられない・急ぎで一括判断が必要な場合の目安は約0.4倍。

恒久化してよい運用(P8時点で3セッション以上の再現性あり)

  1. 見積もり前に「往復が発生する見込みか」を自問する(①の判定)。発生しないなら0.3〜0.4倍を先に適用する
  2. 見積もり前に「設計書に未解決の判断が残っているか」を確認する(③の判定)。残っていなければ複雑度に関わらず標準倍率、残っていれば素直な見積もりに戻す
  3. 「まとめ・完了確認」系タスクは文書更新(定量)とレビュー対応(不定量)を必ず分離する。後者は発見都度・合意値なしで実績のみ記録
  4. 統合・結合系は「結合対象のレビュー済み度合い」を先に確認する(②の判定)
  5. 工程完了前に、その工程で追加した本番コードの未レビュー区間がないか確認する(P6-07・P7-07で実際にバグを検出)
  6. 集約ドキュメント(wbs.mdのB/C振り分け表等)で転記漏れを1件見つけたら、同じ文書内の類似箇所を横展開監査する
