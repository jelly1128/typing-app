# WBS(作業分解構成図)と見積もり

## 計画の方針: ローリングウェーブ

**近い工程は細かく、遠い工程は粗く**分解する。P2 以降のタスクを今から精密に割ろうとしても、要件が固まっていないので必ず外れる。各工程に入る直前に、その工程を時間単位まで分解する。

- **確定済み**: 現在の工程 + 次の工程 → タスク単位(2〜4時間)まで分解し、時間見積もりを持つ
- **暫定**: それ以降 → セッション数のみ

タスク単位の時間見積もりは `/ty-plan` で毎セッション取り、`estimate-actual.md` に記録する。

### 見積もり突き合わせの記録(2026-08-23)

**合計はほぼ一致(10.0 vs 9.5)。差が出たのは配分。** Kazuki は全タスクを一律 1.0h に置き、バッファを別枠 3.0h で持つ形だった。

一律配分 + 一括バッファの問題は精度ではなく、**バッファが誰のものか後から分からない**こと。P1-07 が 3h かかったとき、バッファを消費したのか見積もりが外れたのかを区別できず、ズレ率も補正係数も算出できない。→ **合計 10.0h は Kazuki の値を採用し、バッファを各タスクへ配分した。**

Claude が高く見た根拠:

| ID | 理由 |
|---|---|
| P1-02 | FR-01(ローマ字判定)の要件記述が難物。「し=si/shi/ci を許容」を実装に落とさず曖昧語も使わずに書く必要があり、必ず止まる |
| P1-07 | レビュー実行は5分。**本体は指摘対応**。初回の要件定義書には重要度 A が 5〜10件出る想定 |
| P1-06 | 新機能の初導入は1回で決まらない。書式調査 → 作成 → 起動 → 期待した指摘が出ずプロンプト修正、が入る |
| P1-03 | 観点を並べるのは速いが**値を決めるのが遅い**。「入力遅延 50ms 以下」の 50 の根拠づけ |

**ボトムアップがトップダウンを否定した:** 計画時の P1 は「2〜3セッション(5〜7.5h)」だったが、タスクから積むと 10.0h = **4セッション**。根拠のある積み上げ側を採用し、全体サマリーを修正した。
