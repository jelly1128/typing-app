# ADR-003: userId 推測による他人データ閲覧リスクを受け入れる

## ステータス

採用

## 背景

P2-06a(doc-reviewer によるP2文書一式の再レビュー)の過程で、`api-spec.yaml` の `/api/users/{userId}/...` 系エンドポイント(履歴・自己ベスト・ミス分析)に認可制御がないことが判明した。`userId` を知っている(または連番などで推測できる)第三者は、他人の練習履歴・スコアを閲覧できる。ADR-001 により認証機能自体が MVP スコープ外と既に決定済みだが、認証なしで `userId` ベースの API を公開する場合の閲覧リスクそのものは、ADR-001 では明示的に検討されていなかった。

## 検討した案

| 案 | 内容 | 見送り理由 |
|---|---|---|
| A. 受入リスクとして明記する | 現行 API 仕様のまま進め、リスクを文書化するに留める | (採用) |
| B. `userId` を推測困難な値にする | 連番/UUIDv4 ではなく、ランダムトークン等で発行し実質的な推測を困難にする | 学習用個人開発であり、保存データは名前とタイピングスコアのみで金銭的価値・機微情報を含まない。閲覧されても実害が小さいのに対し、対応にはAPI仕様・テーブル定義の再設計コストが発生し、charter.md 6章の「完走優先」方針に見合わない |
| C. 本格的なアクセス制御を追加する | セッショントークン等で「自分の userId」であることを検証する | ADR-001 で除外した認証機構と実質的に同じ範囲の実装が必要になり、+セッション規模のコストが再発生する |

## 決定

案 A を採用する。`userId` を知っていれば他人の練習履歴・自己ベスト・ミス分析を閲覧できることを**受入リスク**として扱い、charter.md 6章のリスク表に追記する。個人開発・学習目的であり、保存データに金銭的価値や機微情報(パスワード・連絡先等)を含まないため、閲覧されること自体の実害は小さいと判断した。

対応が必要になった場合(例: 公開後に想定外の第三者アクセスが確認された)は、ADR-001 の「本格認証」検討を P9 以降で再検討する形で対応する。

## 影響

- `docs/00_project/charter.md` 6章のリスク表に「userId 推測による他人データ閲覧」を追記する
- `api-spec.yaml` / `screen-design.md` の設計変更は行わない(現行仕様のまま P2 を進める)
- ops-reviewer のレビュー観点には含めない(意図的な受入リスクであり、指摘されるたびにクローズ判断が発生するのを避けるため、ここに決定として固定する)
