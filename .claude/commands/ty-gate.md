工程のレビューゲートを判定する。対象工程: $ARGUMENTS（例: P1。省略時は `progress.md` の現在の工程）

**このコマンドはゲートを通すためのものではなく、通っていないことを見つけるためのもの。** 甘い判定をしない。

## 1. 完了条件を確認する

`workflow.md` から対象工程の**完了条件**と**成果物リスト**を読み取る。

## 2. 成果物の存在と中身を照合する

成果物リストの各ファイルについて、以下を確認する。

- [ ] ファイルが存在するか
- [ ] frontmatter に `doc_id` / `status` / `updated` があるか
- [ ] `docs/_index.md` の台帳に登録され、status が実態と合っているか
- [ ] **中身が完了条件を満たすか**（存在するだけで OK にしない。空セクションや TBD が残っていないか）

## 3. トレーサビリティを確認する

- P2 以降: 設計書の各項目に **FR-ID が併記**されているか
- P4 以降: 全 FR-ID に対応するテストケース ID が1件以上あるか

抜けがあれば具体的に「FR-03 に対応する設計項目がない」の形で列挙する。

## 4. レビューを実施する（P1 / P2 / P3 のゲートのみ）

`.claude/agents/` のレビュアーエージェントを**独立コンテキストで起動**し、成果物ファイルだけを渡す。

- ゲート①（P1後）: `doc-reviewer`
- ゲート②（P2後）/ ③（P3後）: `doc-reviewer` / `test-reviewer` / `ops-reviewer` を並列起動

同じ会話にいる Claude は自分が書いた設計を肯定しやすいため、**必ずサブエージェントに読ませる**。この会話の文脈を渡さないこと。

指摘は `docs/90_review/review-YYYYMMDD_<doc>.md` に以下の形式で記録する。

```
| 指摘ID | 重要度 | 対象箇所 | 指摘内容 | 対応 | ステータス |
|---|---|---|---|---|---|
```

重要度は **A（必須）/ B（推奨）/ C（参考）**。

## 5. 判定を出力する

```
## ゲート判定: （工程ID）

**完了条件:** （workflow.md の1行）

**成果物チェック:**
| 成果物 | 存在 | 中身 | 台帳 |
|---|---|---|---|

**トレーサビリティ:** （抜けの有無）

**レビュー指摘:** A: N件 / B: N件 / C: N件

**判定: 通過 / 不通過**

**不通過の場合、通すために必要なこと:**
1. （具体的に）
```

**通過条件: 成果物が全て揃い、完了条件を満たし、重要度 A の指摘が全件クローズしていること。** 1つでも欠けたら不通過とする。
